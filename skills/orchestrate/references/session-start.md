# Создание плана, запуск и продолжение

Работа начинается с создания плана в сессии проекта. Затем пользователь утверждает проверенный план и запускает его; в следующей сессии продолжает уже запущенную работу. Во всех случаях используются четыре установленных навыка; поставщик и модель ролей выбираются при составлении плана или в начале новой сессии по [протоколу](protocol.md#модель).

В Codex команда начинается с `$orchestrate`, в Claude Code и Antigravity — с `/orchestrate`. Дальше текст одинаковый. Если контракт задаёт другие пути, используйте их. Первый запуск Claude без проектной обёртки описан в инструкции установки; после создания обёртки доступны команды ниже.

## Создание плана

```text
/orchestrate Создай план <имя-плана>. Цель: <результат>. Исполнение не запускай.
```

Оркестратор сам создаёт недостающие документы процесса и определения ролей по [project-files.md](project-files.md). Затем передаёт planner цель, источники и точные пути. Planner создаёт `orchestrate_workflow/plans/<имя-плана>/00_summary.md` и материалы задач; reviewer проверяет план. До этой работы наличие плана не требуется. Если план с таким именем уже существует, читай его и согласуй пересмотр, не заменяя новым.

После положительного ревью оркестратор представляет план пользователю. Пользователь может утвердить его обычной репликой в текущем диалоге; отдельная команда или обязательная формула не нужны. Оркестратор фиксирует ясное согласие в `00_summary.md`. Согласие с планом само по себе не запускает исполнение; если пользователь одновременно явно разрешил запуск, повторную команду не требуй.

### Когда использовать planner

Оркестратор привлекает planner для нового плана или существенного пересмотра: меняются цель, состав и порядок задач или этапов, зависимости, границы работ либо критерии приёмки. Для статуса, восстановления согласованного этапа, записи подтверждённых решений и результатов, исправления ссылок и формулировок без изменения смысла planner не нужен; эти правки выполняет оркестратор. Если восстановление выявило необходимость изменить план по существу, сначала обсуди изменение с пользователем, затем передай пересмотр planner. Пользователю не требуется отдельно вызывать planner или перечислять внутренние роли в поручении.

## Запуск

```text
/orchestrate Запусти утверждённый план <имя-плана> по orchestrate_workflow/plans/<имя-плана>/00_summary.md. Push запрещён.
```

Оркестратор сверяет состояние по порядку ниже и выдаёт задание первого разрешённого этапа. При выполнении утверждённого плана принятые этапы коммитятся и работа продолжается автоматически; явные ограничения пользователя сохраняются. Вопросы — только при новых условиях или конфликтах, требующих решения. Push требует отдельного разрешения.

## Продолжение

```text
/orchestrate Продолжи запущенный план <имя-плана> по orchestrate_workflow/plans/<имя-плана>/00_summary.md. Сначала сверь материал задачи, git, задание, отчёт и ревью.
```

Оркестратор восстанавливает подтверждённое состояние, действующие разрешения и точку продолжения. Открытие новой сессии не отменяет остановку или отмену задания и не разрешает повтор выполненных операций.

## Статус без выполнения

```text
/orchestrate Доложи подтверждённое состояние плана <имя-плана>: открытая задача, отметки её этапов, следующая задача, открытые решения и расхождения с фактом. Исполнение не запускай.
```

Статусный вызов остаётся чтением: не создаёт план, не запускает этапы и не подключает проект.

## Сверка существующего плана

Состояние читается из очереди `orchestrate_workflow/plans/<имя-плана>/00_summary.md` с плановой отметкой `Статус плана`, затем из материала открытой задачи и отметок версии этапов и проверок по [runtimes.md](runtimes.md). Перед вызовом роли проверь контракт, выбранного поставщика и модель роли и наличие его инструмента. Об исчерпании лимита судят по ответу вызова; замена — по [протоколу](protocol.md#модель).

1. При порученной подготовке или работе обеспечить недостающие файлы проекта по [project-files.md](project-files.md); статусное чтение их не создаёт. Прочитать `AGENTS.md`, `orchestrate_workflow/method.md` и папку названного плана: `00_summary.md` со статусом плана, очередь и материал текущей задачи с отметками этапов.
2. Сопоставить отметки с `git log`, HEAD, рабочим деревом и каталогом текущей сессии этого плана. Для `spec.md`, `result.md`, `review.md` проверить точное совпадение `План`, `Задача`, `Этап`, исходного `HEAD` и описания исходного рабочего дерева.
3. Не интерпретировать другие файлы в каталогах плана или сессии как состояние workflow без явной ссылки из `00_summary.md`, материала задачи, `spec.md` или протокола.
4. До первого задания сверить всё поручение с фактом: что уже выполнено, что осталось, какие существующие изменения принадлежат этапу, какие разрешения продолжают действовать. Прочитать вызываемые сценарии и проверить, какие операции они уже повторяют внутри. Не добавлять backup, новые копии состояния и другие операции среды без требования или установленной необходимости; способ доказательства не превращать в отдельное требование продукта. Для сравнения до/после заранее определить обе точки состояния, одинаковые исходные данные и обработку показателей, зависящих от времени.
5. Доложить подтверждённое состояние и расхождения.
6. Запускать новый этап только для плана со статусом `утверждён`. Продолжать только ранее запущенные этапы в разрешённых границах. Новое существенное решение сначала представить пользователю.

Если каталога текущей сессии нет, не объявляй задачу неначатой: отметки в папке плана и история git хранят подтверждённое состояние.

Если идентификаторы задания и отчётов не совпадают, старый отчёт не принимается. Сначала выясни результат и состояние ранее вызванной роли.

При обрыве не повторяй операции со средой только потому, что отчёта нет.

Новая задача готовится в материале под git, проходит ревью и утверждение. Очередь содержит ссылку, а не вторую копию этапов. Отдельный локальный план и копии будущих заданий не создаются.

После приёмки состояние пишется в материал задачи, и один коммит фиксирует результат вместе со статусом, если пользователь явно не запретил коммиты. При запрете записываются приёмка без коммита, причина и проверенная версия; следующий этап получает установленную исходную точку с перечисленными правками по протоколу. При закрытии материал остаётся на прежнем пути. Следующий исполнитель получает новый `spec.md` и новый контекст.

Отрицательное ревью, недоступная проверка и неизвестный результат обрыва требуют разных действий, а не общего «повторить этап».

Перед вопросом о решении проверь `AGENTS.md`, предметный источник и последние решения. Повтор согласованного не запрашивай. Если инструмент вернул отказ, назови конкретное действие и границу отказа. Не утверждай, что пользователь не разрешил всю задачу.

Точку продолжения бери из материала текущей задачи, включая записанный порядок восстановления. Старое положительное ревью не отменяет оформленный возврат. До вызова исполнителя сверь путь каталога текущей сессии и состояние обязательных `spec.md`, `result.md`, `review.md` с привязкой и текущим заданием; установленные пути повторно не согласуются. Прежний отчёт не выдавай за результат нового задания.

Одновременная запись двух orchestrator-сессий в один план не поддерживается. Если тот же план уже ведётся другой активной orchestrator-сессией, второй вызов ограничивается чтением и статусом до явной передачи управления.
