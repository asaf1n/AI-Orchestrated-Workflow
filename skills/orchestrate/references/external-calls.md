# Вызов ролей и параметры runtime

Вызов роли всегда получает новое независимое поручение, точный установленный `SKILL.md`, `AGENTS.md`, критерии, версию файлов и границы доступа. Проектная привязка обязательна для этапа; ревью плана или инструкций без подключённого workflow использует назначенные входы без привязки и файлов этапа. Роли не выбирают себе модель и не запускают вложенную оркестрацию.

Новый контекст — свойство вызова. Допустимы отдельный процесс CLI и встроенный субагент, который стартует без истории вызывающей сессии. Режимы, наследующие историю вызывающей сессии (`fork` в Claude Code и аналоги), для ролей не применяются. Orchestrator фиксирует фактический режим контекста вместе с профилем модели; если режим не подтверждён, независимость роли в отчёте указывается как неустановленная.

Режим подтверждается параметрами вызова, а не ответом роли. Доказательство — сохранённая фактическая команда или параметры вызова: для CLI — новый процесс без продолжения сессии (`--continue`/`--resume` в Claude Code, `exec resume` в Codex, `--conversation` в Antigravity CLI); для встроенного субагента — тип вызова без наследования истории. После установки или смены версии runtime выполняется контрольный вызов: в историю вызывающей сессии вносится метка, отсутствующая в поручении, и роль сообщает все известные ей метки. Названная метка доказывает наследование истории; режим запрещается до устранения причины.

Выбери модель по [models.md](models.md), затем подходящий доступный runtime. Встроенный субагент допускается, если соответствует профилю, позволяет требуемую изоляцию и разрешения. `inherit` не подтверждает конкретную модель. Внешний CLI применяй при необходимости другого поставщика, effort или канала. Переключение runtime не должно обходить отказ прав доступа.

| Runtime | Вызов одного поручения |
|---|---|
| Claude Code | `claude -p --model <id> --effort <supported-level> --permission-mode <policy>` |
| Codex | `codex exec -m <id> -c model_reasoning_effort="<supported-level>" -s <sandbox>` |
| Antigravity CLI | `agy -p "<задание>" --model <slug> --output-format json` с `--effort <level>` только если поддерживается |

Роль Planner может записывать назначенные материалы; Implementer — назначенные файлы и результат; Reviewer — только назначенное заключение (либо итоговый ответ read-only). Для каждого CLI проверяй текущие `--help`, каталог моделей, код выхода, stdout, stderr, фактическую модель и влияние разрешений. Если разрешение отклонено, код 0 сам по себе не подтверждает выполнение.

Antigravity `invoke_subagent` использует только модели, доступные внутреннему субагенту. Поставщик сам по себе не определяет канал: внешний CLI нужен при явном закреплении runtime или отсутствии нужного профиля во встроенном API. Допустимые значения модели проверяй по схеме установленного runtime; псевдонимы не означают конкретный выпуск модели или поставщика. Для внутреннего Reviewer указывай проверенные имена `tools` и исключай инструменты изменения продукта. Определения находятся в `.agents/agents/` (workspace) или `~/.gemini/config/agents/` (global). Составной Orchestrator — режим одной сессии с неизменяемым effort; он не заменяет независимого Reviewer.

## Интерактивная сессия Planner

Интерактивная сессия — отдельный процесс runtime, который пользователь запускает в корне проекта по команде Orchestrator. Сессия стартует без истории вызывающей сессии; продолжение сессий (`--continue`, `--resume`, `exec resume`, `--conversation`) для неё не применяется. Runtime запускается в режиме планирования: вопросы задаются его инструментом структурированных вопросов, а запись начинается только после одобрения черновика в сессии и ограничивается порученными материалами плана и отчётом. Технический запрет записи на этапе разведки зависит от runtime: в Claude Code его обеспечивает `--permission-mode plan` (до явного одобрения записи), в Codex — режим `Plan` (`/plan` в TUI) с политикой одобрений или sandbox, в Antigravity CLI `--mode=plan` задаёт инструктивный режим поверх действующих разрешений.

| Runtime | Запуск | Вопросы пользователю |
|---|---|---|
| Claude Code | `claude --permission-mode plan --model <id> --effort <supported-level> "/planner <путь поручения>"` | `AskUserQuestion` |
| Codex | `codex -m <id> -c model_reasoning_effort="<supported-level>"`, до первого хода — `/plan` в TUI, затем `$planner <путь поручения>` | `request_user_input`, доступен только в режиме Plan |
| Antigravity CLI | `agy --mode=plan --model <slug> --effort <supported-level> -i "/planner <путь поручения>"` | вопросы режима планирования |

Флаги и способ передачи начального запроса проверяй по `--help` установленной версии; `--effort` передаётся только если применим к выбранному режиму и модели. Одобрение черновика в сессии не является утверждением плана. Режим контекста подтверждается сведениями о фактическом запуске (подтверждённой командой или метаданными сессии без её продолжения); при наличии только выданной команды без подтверждения запуска изоляция указывается как неподтверждённая. Фактическая модель подтверждается метаданными runtime; при их отсутствии она указывается как неподтверждённая. Без присутствия пользователя Planner вызывается автономно, как одно поручение.

## Внешний контроллер Antigravity

Поддерживается MCP-мост `bridge/` репозитория комплекта (описание — `bridge/README.md`; в установленный каталог навыков не копируется). Он передаёт из удалённого LLM-чата запрос в `agy -p "/orchestrate ..."` и продолжает зарегистрированную сессию через `--conversation <id>`. Единственный владелец плана — эта `agy`-сессия; внешний клиент не запускает вторую оркестрацию. Мост сериализует вызовы, сохраняет соответствие плана и conversation ID, проверяет завершение и сообщения об отказе.

Headless CLI использует заранее настроенные разрешения. Не отключай контроль подтверждений, не меняй авторизацию и не передавай секреты в промпте. Открытый HTTP без аутентификации запрещён; удалённый доступ требует защищённого TLS-шлюза. Для новых задач `/orchestrate` вызывается явно, так как навык может запрещать неявную активацию.

## Альтернативные аккаунты внешних CLI

Внешние сессии (`claude -p`, `codex exec`, интерактивные сессии Planner) запускает только Orchestrator. Если пользователь заводит дополнительный аккаунт поставщика, Orchestrator выбирает его для одного вызова переменной окружения, заданной только в окружении этого вызова:

| Runtime | Переменная | Каталог аккаунта (пример) |
|---|---|---|
| Claude Code | `CLAUDE_CONFIG_DIR` | `%USERPROFILE%\.claude-alt` |
| Codex | `CODEX_HOME` | `%USERPROFILE%\.codex-alt` |

- По умолчанию вызовы идут по основному аккаунту; альтернативный применяется по указанию пользователя в сессии либо при исчерпании квоты основного (см. «Обработка сбоев»). Глобальные и постоянные переменные окружения не меняются.
- Перед первым применением проверь вход безобидным вызовом без данных проекта (`claude auth status`, `claude -p "Ответь одним словом: OK"`; `codex login status`, `codex exec -s read-only --skip-git-repo-check "Ответь одним словом: OK"`) и зафиксируй каталог аккаунта в отчёте вызова; учётные данные и содержимое `auth.json` не читай и не выводи.
- Песочница Codex `workspace-write` (значение по умолчанию в `config.toml`) может не пропускать доступ к локальным службам, например к named pipe Docker на Windows. Если задание этапа требует такого доступа, Orchestrator задаёт `-s danger-full-access` только в команде этого вызова `codex exec`, не меняет `config.toml` аккаунта и фиксирует режим в отчёте вызова; иначе остаётся `workspace-write`. Вместо этого допустим переход на Claude Code по правилам «Обработка сбоев».
- Встроенные субагенты runtime (`Agent` в Claude Code, `invoke_subagent` в Antigravity) и сама сессия Orchestrator работают под аккаунтом, с которым запущена сессия; из сессии он не переключается. Для смены аккаунта этой сессии её перезапускают с нужной переменной окружения.
- Каталог альтернативного аккаунта содержит собственную конфигурацию runtime: скопируй в него только нужные навыки, определения ролей и `config.toml`, без секретов других сервисов.

## Обработка сбоев

Сохрани частичный результат и реальный статус. Отказ модели, отказ runtime, нехватка квоты, блокировка permissions и падение предметной проверки требуют разных действий. При лимите квоты во внешнем CLI переключись на доступный внутренний канал той же модели (например, `agy`) либо резерв того же класса по [models.md](models.md) автоматически, без выноса переключения на согласование пользователю. Автоматическая замена на другую модель не создаёт подтверждения жёстко закреплённого профиля. Не повторяй завершённые операции без сверки их последствий.
