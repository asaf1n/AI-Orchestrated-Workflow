# Внешние вызовы и запуск ролей

Справочный материал оркестратора; читается по ссылке из [SKILL.md](../SKILL.md). Роли не читают эти файлы для исполнения своего протокола; reviewer читает их, когда они назначены объектом ревью инструкций.

## Выбор способа запуска роли

По умолчанию роль запускает встроенный субагент runtime: определение из `.claude/agents` или `.codex/agents`, доступный API Antigravity. Он даёт новый контекст при общем workspace. Перед вызовом проверь фактическую схему выбора модели и усилия; наследование допустимо лишь при подтверждённом совпадении хост-профиля с выбранным профилем роли. Поставщик модели не определяет канал запуска: внутренний Claude в Antigravity и Claude Code относятся к разным runtime. Внешний неинтерактивный CLI нужен, если он закреплён в поручении или проектной привязке, требуется независимый канал квоты либо встроенный API не поддерживает нужный профиль. Постоянный выбор runtime в `orchestrate_workflow/method.md` применяется автоматически. При недоступности CLI используй следующую разрешённую альтернативу из поручения; по умолчанию действует очередь сценария из [models.md](models.md). Встроенный субагент с отличающимся профилем не заменяет назначенную модель неявно. Ограничения пользователя имеют приоритет; если разрешённых вариантов нет, сохрани точку продолжения и назови блокер. Причину и целевой профиль внешнего вызова укажи в spec.md для implementer, в отдельном поручении — для planner или reviewer.

## Внешние вызовы

Используй отдельный неинтерактивный запуск в корне проекта. В промпте назови точный SKILL.md роли, корень, режим, входы и пути обмена; не переписывай туда вместо файла всё задание. Новый контекст не подменяется продолжением прежнего агента.

| Инструмент | Planner: план и материалы | Implementer: этап | Reviewer: проверка |
|---|---|---|---|
| Claude Code | claude -p --model <модель> --effort <low\|medium\|high\|xhigh> --permission-mode acceptEdits | claude -p --model <модель> --effort <low\|medium\|high\|xhigh> --permission-mode acceptEdits | claude -p --model <модель> --effort <low\|medium\|high\|xhigh> --permission-mode plan; только разрешённое чтение и проверки |
| Codex | codex exec -m <модель> -c model_reasoning_effort="<low\|medium\|high\|xhigh>" -s workspace-write | codex exec -m <модель> -c model_reasoning_effort="<low\|medium\|high\|xhigh>" -s workspace-write | codex exec -m <модель> -c model_reasoning_effort="<low\|medium\|high\|xhigh>" -s read-only -o <путь заключения> |
| Antigravity CLI | agy -p --model <идентификатор> --effort <low\|medium\|high> --mode accept-edits | agy -p --model <идентификатор> --effort <low\|medium\|high> --mode accept-edits | agy -p --model <идентификатор> --effort <low\|medium\|high> --mode plan --output-format json |

Уровень усилия разрешается в конкретный флаг/параметр целевого CLI (`low`, `medium`, `high`, `xhigh`) вместо неявного «обычного уровня». Учитывай только поддерживаемые моделью уровни: для Gemini в Antigravity поддерживаются исключительно `low`, `medium`, `high` (уровень `xhigh` не предполагается и не поддерживается); для моделей других поставщиков из каталога `agy models` допустимые уровни сверяются с каталогом и `--help`.

Запрещена активация режимов вложенной авто-оркестрации и динамических workflow во внешних CLI (таких как `ultracode`, сторонние мультиагентные надстройки или автономные циклы перепланирования). Внешний вызов получает одно ограниченное поручение: planner — подготовку либо пересмотр плана без запуска исполнения, implementer — один этап, reviewer — независимую проверку. Ведение процесса и запуск следующих ролей остаются у оркестратора.

Перед использованием сверяй `--help`, `--version`, актуальный каталог моделей и параметры вызова, путь executable, код выхода и реальный ответ. В проверке вызова обязательно фиксируй явно переданные флаги модели и усилия в команде запуска. Проверяй вывод (`stdout` и `stderr`) на отсутствие предупреждений о тихом fallback/даунгрейде (сброс или занижение усилия reasoning, автоматическая замена запрошенной модели на дефолтную, игнорирование переданных параметров). При обнаружении тихого fallback сохрани вывод и метаданные: успешно полученный результат не пропадает, но запрошенный профиль не считается подтверждённым. Отдельно проверь обязательные требования к модели, поставщику и независимости; при их нарушении не засчитывай только соответствующий критерий. При ошибке запуска, незавершённой команде или отсутствии результата вызов остаётся неуспешным. Наличие CLI или расширения не доказывает доступ к модели. Авторизацию и настройки разрешений ради обхода отказа не меняй; секреты не читай и не публикуй. Флаги обхода подтверждений и песочницы не используются.

В Windows PowerShell закрывай stdin: `$null | <CLI> ...`. Сохраняй stdout и stderr отдельно, а код CLI сразу после его завершения; последующая команда его не заменяет. Отчёты записываются UTF-8 без BOM через явный UTF8Encoding; не полагайся на кодировку `>` или версии PowerShell. Для JSON сохраняй только содержимое result/response в заключение, сохранив метаданные и ошибку отдельно. При ненулевом коде сохранённый файл не является успешным отчётом.

Внешний ревьювер возвращает полное заключение итоговым ответом; инструмент/оркестратор сохраняет его без правки. До и после вызова сравни SHA-256 проверяемых файлов; spec.md и result.md сравни для ревью этапа, если эти файлы относятся к поручению. Для ревью плана или инструкций используй назначенные материалы, не требуя ещё не существующие spec.md/result.md. Чтение установленного комплекта вне workspace должно быть реально разрешено; при отказе назови действие и причину, не расширяй режим. Шаблон промпта: «Выполни независимое ревью прямо сейчас за один запуск по <SKILL.md>, <входам> и <критериям>. Только чтение. Выбери вердикт по фактам. Верни заключение по форме навыка».

Python `.venv` может ссылаться на внешний базовый interpreter: для разрешённого Codex-вызова используй `--add-dir` с `home` из pyvenv.cfg, если требуется этой песочницей. Недоступные CLI сначала проверяются по известному пути установки; настройка shim выполняется только в рамках порученного подключения.

На Windows известные пути проверки: `%LOCALAPPDATA%/OpenAI/Codex/bin/*/codex.exe`, `~/.gemini/bin/agy.exe`; shims при порученном подключении — `~/.local/bin/codex.cmd`, `~/.local/bin/agy.cmd`. Проверяй текущую установку, а не предполагай существование бинарника по этому шаблону.
