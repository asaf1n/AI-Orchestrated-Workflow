# Вызов ролей и параметры runtime

Вызов роли всегда получает новое независимое поручение, точный установленный `SKILL.md`, `AGENTS.md`, критерии, версию файлов и границы доступа. Проектная привязка обязательна для этапа и при ревью в подключённом workflow; для ревью плана или инструкций файлы этапа (`spec.md`, `result.md`) не требуются, а без подключённого workflow используются назначенные входы без привязки. Внеролевая read-only разведка (`task: context` из [models.md](models.md)) выполняется без ролевого `SKILL.md` и без прав записи. Роли не выбирают себе модель и не запускают вложенную оркестрацию.

Новый контекст — свойство вызова. Допустимы отдельный процесс CLI и встроенный субагент, который стартует без истории вызывающей сессии. Режимы, наследующие историю вызывающей сессии (`fork` в Claude Code и аналоги), для ролей не применяются. Orchestrator указывает применённый режим контекста при необходимости для независимой оценки; неподтверждённую независимость не объявляет доказанной.

Режим подтверждается параметрами вызова, а не ответом роли. Отдельный новый процесс CLI без продолжения чужой сессии (`--continue`/`--resume` в Claude Code, `exec resume` в Codex, `--conversation` в Antigravity CLI) или встроенный субагент без наследования истории обеспечивает необходимую изоляцию. Проверяй фактический режим, когда это влияет на независимость. Если режим изоляции неизвестен или есть свидетельство наследования чужой истории, проверь его точечно. Не делай тест с метками и не сохраняй доказательство для каждого запуска.

Выбери профиль по [models.md](models.md), затем подходящий доступный runtime. Встроенный субагент допускается, если соответствует профилю, позволяет требуемую изоляцию и разрешения. `inherit` не подтверждает конкретную модель. Внешний CLI применяй при необходимости другого поставщика, доступного `effort` или канала. Переключение runtime не должно обходить отказ прав доступа. Передача флагов выбора модели и `effort` применяется только в тех runtime, которые их поддерживают; для runtime с фиксированным или управляемым профилем смена модели и `effort` не требуются.

| Runtime | Вызов одного поручения |
|---|---|
| Claude Code | `claude -p [--model <id>] [--effort <supported-level>] --permission-mode <policy>` |
| Codex | `codex exec [-m <id>] [-c model_reasoning_effort="<supported-level>"] -s <sandbox>` |
| Antigravity CLI | `agy -p "<задание>" [--model <slug>] [--effort <supported-level>] --output-format json` |
| Docker Agent (`cagent`) | `docker agent run --exec --last --json [--model <provider/model>] --safety <policy> <agent-ref\|config.yaml> "<задание>"` |

Роль Planner может записывать назначенные материалы и `Путь отчёта`; Implementer — назначенные файлы и результат; Reviewer — только назначенное заключение (либо итоговый ответ read-only). При первом подключении, обновлении runtime или ошибке проверь `--help` и каталог моделей (если есть). После исполнения проверяй результат и код завершения; полный журнал stdout/stderr и модельную телеметрию не сохраняй без необходимости. Если разрешение отклонено, код 0 сам по себе не подтверждает выполнение. Для `docker agent` в read-only и неинтерактивных проверках используй `--safety restricted` и read-only набор инструментов (`git`, чтение без записи); для файловой изоляции параллельных задач доступен `--worktree`.

Песочница Codex `workspace-write` (значение по умолчанию в `config.toml`) может не пропускать доступ к локальным службам, например к named pipe Docker на Windows. Если задание этапа требует такого доступа, Orchestrator применяет `-s danger-full-access` только при явном разрешении в `orchestrate_workflow/method.md` или от пользователя, передаёт флаг только в команде этого вызова `codex exec` без изменения `config.toml` и фиксирует режим в `spec.md` и отчёте вызова (иначе остаётся `workspace-write` либо используется другой разрешённый runtime, заранее допущенный для таких проверок).

Antigravity `invoke_subagent` использует только модели, доступные внутреннему субагенту. Поставщик сам по себе не определяет канал: внешний CLI нужен при явном закреплении runtime или отсутствии нужного профиля во встроенном API. Допустимые значения модели проверяй по схеме установленного runtime; псевдонимы не означают конкретный выпуск модели или поставщика. Для внутреннего Reviewer указывай проверенные имена `tools` и исключай инструменты изменения продукта. Определения находятся в `.agents/agents/` (workspace) или `~/.gemini/config/agents/` (global). Составной Orchestrator — режим одной сессии с неизменяемым effort; он не заменяет независимого Reviewer, когда такой Reviewer действительно назначен.

## Контейнерные и специализированные инструменты Docker

- **Docker Agent (`docker agent`) и Docker Model Runner (`docker model`)**: опциональный CLI-канал для подключения альтернативных поставщиков (open-weights, OpenRouter, пользовательский шлюз `--models-gateway`) и локальных моделей (`dmr`) — прежде всего для класса `utility`, приватных/офлайн-сценариев и резервного `executor`. Перед первым включением в роли проверь `docker agent doctor`, `docker agent models`, возвращаемые JSON-метаданные и контрольный тест свежего контекста.
- **Docker AI (`docker ai` / Gordon)**: управляемый интерактивный помощник без выбора модели, настройки `effort` и JSON-метаданных, работающий с интерактивным подтверждением команд и окнами квот Docker. Применяется точечно (интерактивно или для разовых диагностических запросов) для обслуживания локального Docker Desktop, разбора логов и сбоев контейнеров, оптимизации `Dockerfile` и миграции на Docker Hardened Images (DHI) — без требования смены модели/`effort`. Не применяется для автоматического headless-ревью и этапов, требующих подтверждённой модели либо технической read-only изоляции.
- **Инструментальный слой Docker для штатных ролей**: в задачах контейнеризации и Kubernetes роли Implementer и Reviewer напрямую используют CLI-плагины среды (`docker scout`, `docker dhi`, `docker compose bridge convert`) и контейнеризованные MCP-серверы через **Docker MCP Toolkit** (`docker mcp gateway`, включая read-only K8s MCP-серверы для `get`/`describe`/`diff`/`logs`/`events`) в рамках своих границ доступа.

## Интерактивная сессия Planner

Интерактивная сессия — отдельный процесс runtime, который пользователь запускает в корне проекта по команде Orchestrator. Сессия стартует без истории вызывающей сессии; продолжение сессий (`--continue`, `--resume`, `exec resume`, `--conversation`) для неё не применяется. Runtime запускается в режиме планирования: вопросы задаются его инструментом структурированных вопросов, а запись начинается только после одобрения черновика в сессии и ограничивается порученными материалами плана и отчётом. Технический запрет записи на этапе разведки зависит от runtime: в Claude Code его обеспечивает `--permission-mode plan` (до явного одобрения записи), в Codex — режим `Plan` (`/plan` в TUI) с политикой одобрений или sandbox, в Antigravity CLI `--mode=plan` задаёт инструктивный режим поверх действующих разрешений.

| Runtime | Запуск | Вопросы пользователю |
|---|---|---|
| Claude Code | `claude --permission-mode plan [--model <id>] [--effort <supported-level>] "/planner <путь поручения>"` | `AskUserQuestion` |
| Codex | `codex [-m <id>] [-c model_reasoning_effort="<supported-level>"]`, до первого хода — `/plan` в TUI, затем `$planner <путь поручения>` | `request_user_input`, доступен только в режиме Plan |
| Antigravity CLI | `agy --mode=plan [--model <slug>] [--effort <supported-level>] -i "/planner <путь поручения>"` | вопросы режима планирования |

Флаги и способ передачи начального запроса проверяй по `--help` установленной версии; параметры модели и `effort` передаются только если поддерживаются выбранным runtime и применимы к режиму. Одобрение пользователем в интерактивной сессии можно учитывать как решение по плану; не требуется просить то же одобрение повторно без изменения целей или условий. Для важной независимой оценки подтвердите, что вызван новый контекст; вывод модели о собственной независимости не является доказательством. Фактическую модель указывай только при наличии данных runtime. Без присутствия пользователя Planner вызывается автономно, как одно поручение.

## Внешний контроллер Antigravity

Поддерживается MCP-мост `bridge/` репозитория комплекта (описание — `bridge/README.md`; в установленный каталог навыков не копируется). Он передаёт из удалённого LLM-чата запрос в `agy -p "/orchestrate ..."` и продолжает зарегистрированную сессию через `--conversation <id>`. Единственный владелец плана — эта `agy`-сессия; внешний клиент не запускает вторую оркестрацию. Мост сериализует вызовы, сохраняет соответствие плана и conversation ID, проверяет завершение и сообщения об отказе.

Headless CLI использует заранее настроенные разрешения. Не отключай контроль подтверждений, не меняй авторизацию и не передавай секреты в промпте. Открытый HTTP без аутентификации запрещён; удалённый доступ требует защищённого TLS-шлюза. Для новых задач `/orchestrate` вызывается явно, так как навык может запрещать неявную активацию.

## Альтернативные аккаунты внешних CLI

Внешние сессии (`claude -p`, `codex exec`, интерактивные сессии Planner) запускает только Orchestrator. Если пользователь заводит дополнительный аккаунт поставщика, Orchestrator выбирает его для одного вызова переменной окружения, заданной только в окружении этого вызова:

| Runtime | Переменная | Каталог аккаунта (пример) |
|---|---|---|
| Claude Code | `CLAUDE_CONFIG_DIR` | `%USERPROFILE%\.claude-alt` |
| Codex | `CODEX_HOME` | `%USERPROFILE%\.codex-alt` |

- По умолчанию вызовы идут по основному аккаунту; альтернативный применяется по указанию пользователя в сессии либо при исчерпании квоты основного (см. «Обработка сбоев»). Глобальные и постоянные переменные окружения не меняются.
- Перед первым применением проверь вход безобидным вызовом без данных проекта (`claude auth status`, `claude -p "Ответь одним словом: OK"`; `codex login status`, `codex exec -s read-only --skip-git-repo-check "Ответь одним словом: OK"`) и зафиксируй каталог аккаунта в отчёте вызова; учётные данные и содержимое `auth.json` не читай и не выводи.
- Встроенные субагенты runtime (`Agent` в Claude Code, `invoke_subagent` в Antigravity) и сама сессия Orchestrator работают под аккаунтом, с которым запущена сессия; из сессии он не переключается. Для смены аккаунта этой сессии её перезапускают с нужной переменной окружения.
- Каталог альтернативного аккаунта содержит собственную конфигурацию runtime без секретов других сервисов: для Claude Code (`CLAUDE_CONFIG_DIR`) — навыки, определения ролей, `CLAUDE.md` и настройки; для Codex (`CODEX_HOME`) — навыки, определения ролей, `AGENTS.md` и `config.toml`.

## Сбои и лимиты

Различай отказ инструмента, ограничения разрешений, ошибку продукта и лимит модели. Не обходи sandbox или авторизацию ради продолжения.

1. Если основной канал исчерпал квоту, используй заранее доступный разрешённый аккаунт, совместимый runtime или резервную модель по [models.md](models.md). Сохраняй текущие изменения, не повторяй совершённые операции.
2. Если разрешённые каналы недоступны, сообщи блокер, сохранённый результат и точку возобновления. **Не ставь многочасовое ожидание квоты и таймер пробуждения автоматически.** Ожидание возможно по явному поручению пользователя в среде, поддерживающей такое выполнение.
3. После восстановления сверяй фактическое состояние, а не только отчёт предыдущей роли. Проверяй повторно лишь незавершённое или изменившееся.
