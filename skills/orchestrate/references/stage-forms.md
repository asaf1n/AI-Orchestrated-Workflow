# Формы поручений

## Поручение Planner

Передаётся текстом вызова либо временным файлом среды; в `orchestrate_workflow/<план>/` не сохраняется. То же поручение и отчёт/ответ Planner получает Reviewer плана.

```markdown
# Поручение Planner: <план>
Режим: новый план | существенный пересмотр
Вызов: интерактивная сессия | автономный
Путь отчёта: <временный файл среды для интерактивной сессии> | ответ вызова
Базовая версия плана: <коммит утверждённой редакции> | нет
Исходный запрос: <дословно либо точная ссылка на сообщение пользователя>
Цель и ограничения: <в формулировке пользователя; разрешения и запреты>
Подтверждённые решения: <решение, кем и когда подтверждено> | нет

## Основание пересмотра
| Требование | Источник | Затронутые задачи и этапы |
|---|---|---|

## Установленные факты
| Факт | Источник и версия | Способ проверки |
|---|---|---|

## Неизвестное и разногласия
- <вопрос> | нет

## Источники и проверенный доступ
<Пути, БД, сервисы, разделы, коммиты или даты; команда и фактический результат реальной предплановой проверки наличия и подключения на чтение>

## Можно менять
<Пути материалов плана; для интерактивной сессии — также Путь отчёта>

## Профиль
<Runtime, режим контекста; поставщик, model ID и effort — если поддерживаются runtime, иначе «фиксированный/управляемый профиль»>
```

Факты поручения — входные данные Planner, а не выводы плана. Предполагаемая структура плана и желаемые выводы в поручение не включаются, если их не утвердил пользователь. Крупные журналы и выгрузки передаются путём, а не содержимым. Раздел «Основание пересмотра» заполняется при пересмотре; для нового плана указывается «нет».

## Задание этапа

Полевая форма `spec.md` для Implementer. Профиль Reviewer задаётся в отдельном поручении.

```markdown
# Этап <имя>

План: `<план>`
Задача: `<задача>`
Материал: `orchestrate_workflow/plans/<план>/<задача>.md`
Этап: `<этап>`
Исходный HEAD: `<commit>`
Исходное рабочее дерево: <снимок, перечень правок и принадлежность>
Состояние материала на момент выдачи: <состояние>

## Сделать
<Граница, исходные решения, порядок исполнения, окружение и перенесённые из плана критерии готовности>

## Модель и альтернативы
Основная: <runtime; поставщик, model ID и effort — если поддерживаются runtime, иначе «фиксированный/управляемый профиль»; при необходимости разрешённый режим песочницы>
Резерв: <если нужен, условие и профиль; иначе «не задан»>

## Можно менять
<Точные пути; при параллельном запуске — также путь собственного `result.md` в `orchestrate_workflow/<план>/runs/<id>/` и выделенный worktree при наличии>

## Общие ресурсы
<Ресурс, контур, доступ, владелец и порядок передачи; если нет — «нет»>

## Проверки
<Перенесённые из плана критерии проверки: конкретные команды, пути, имена тестов, значения параметров и ожидаемый результат>

## Восстановление
<Только при продолжении>

## Не делать
<Ограничения и запреты проекта>
```

Не расширяй права роли через подстановку модели. «Сделать» и «Проверки» переносят конкретные критерии из плана без потери команд, путей, имён тестов, значений параметров и ожидаемых результатов, добавляя порядок исполнения и окружение. При параллельном запуске независимых задач каждая ветка использует собственные `spec.md`, `result.md` и `review.md` в подкаталоге `orchestrate_workflow/<план>/runs/<id>/`, зарегистрированном в `state.md`; пять обязательных идентификаторов сохраняются без изменения в `result.md` и `review.md`. При повторном вызове после остановки уточни полный `spec.md`, установи состояние предыдущего исполнителя и только затем замени его отчёт строкой ожидания.

Строка ожидания целиком заменяет файл отчёта вызываемой роли (`result.md`, `review.md` или `review_plan.md`):

```markdown
Ожидание отчёта <исполнителя или ревьювера>. План: `<план>`. Задача: `<задача>`. Этап: `<значение из spec.md>`. Предыдущий текст к этому вызову не относится.
```

Для `review_plan.md` (без задачи и этапа):

```markdown
Ожидание отчёта ревьювера плана. План: `<план>`. Предыдущий текст к этому вызову не относится.
```
