# Подключение проекта

В проекте достаточно `AGENTS.md` и при необходимости `orchestrate_workflow/method.md`; общие навыки устанавливаются отдельно. План готовит Planner, когда задача требует декомпозиции, а не по каждому запросу состояния.

Штатные пути:

| Назначение | Путь |
|---|---|
| Привязка | `orchestrate_workflow/method.md` |
| Очередь задач | `orchestrate_workflow/plans/<план>/00_summary.md` |
| Задачи и этапы | `orchestrate_workflow/plans/<план>/<задача>.md` |
| Текущая сессия при необходимости | `orchestrate_workflow/<план>/state.md`, `spec.md`, `result.md`, `review.md`, `review_plan.md` (для параллельных задач при необходимости — слоты `runs/<id>/`) |

Каталог плана `orchestrate_workflow/plans/<план>/` версионируется и содержит только последовательность действий и признак утверждения без хронологии и оперативных статусов. Каталог текущей сессии используется для долгих работ, восстановления и передачи; его временные файлы не нужно версионировать. Незаконченные результаты не стирай при повторном подключении. Имя `plans` зарезервировано.

## Определения ролей

Для Codex: `.codex/agents/<роль>.toml` с `name`, `description`, `developer_instructions`. Для Claude: `.claude/agents/<роль>.md` с frontmatter и путём установленного навыка. Для Antigravity: `.agents/agents/<роль>.md` или `~/.gemini/config/agents/<роль>.md` с `name`, `description`, `subagent: true`, поддерживаемой моделью и проверенным `tools`.

Тонкий адаптер сообщает агенту: «Прочитай установленный SKILL.md своей роли, AGENTS.md, при наличии orchestrate_workflow/method.md и заданные пути; действуй только в разрешённой границе». Не копируй протокол в определение. Если задача требует конкретной модели или `effort` и профиль хоста с ними не совпадает, не используй неконтролируемое `inherit` — вызови роль через совместимый CLI (для runtime с фиксированным профилем смена модели и `effort` не требуются). Наличие файла без реального обнаружения не доказывает подключение.

Для Reviewer необходимы действующие требования и проверяемый результат; отдельные `spec.md` и `result.md` необязательны, если данные переданы в поручении. Для ревью плана или инструкций файлы этапа не требуются, а проектная привязка используется при подключённом workflow (без него достаточно назначенных материалов). Исходники навыков, включая Orchestrator и `references/`, могут быть объектом аудита без передачи управления процессом.

## method.md

```markdown
# Привязка проекта <имя>

## Пути
<Только отклонения от штатных путей>

## Предметный контракт
<Точные документы, команды, ресурсы и дополнительные критерии>

## Профили и ограничения
<При необходимости закреплённые поставщики, модели, runtime,
режимы разрешений и ограничения; иначе «по общему протоколу»>

## Формат отчёта
<Только если у проекта есть собственные требования>
```

Не дополняй привязку вымышленными путями и правилами. Пользовательские настройки и существующие определения ролей сохраняй. Примеры в `examples/` предназначены для адаптации, а не слепого копирования.
