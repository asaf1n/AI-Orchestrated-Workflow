# Выбор моделей и альтернатив

Модель выбирается для конкретной роли и задачи. Роль, класс возможностей, effort, runtime и поставщик — разные свойства; имена выпусков моделей не являются частью протокола.

| Класс | Назначение |
|---|---|
| `senior` | Сложная архитектура, планирование при высокой неопределённости, арбитраж |
| `executor` | Код, SQL, тесты, документация и ограниченные изменения по заданным критериям |

Составной режим runtime (например, Antigravity Orchestrator) не является третьим классом качества: он связывает планирующую и исполнительскую модели внутри **одной** сессии. Этот внутренний процесс не заменяет отдельных Planner и Reviewer. У составного режима `effort` может быть фиксированным.

## Профиль

До вызова роли определи:

1. `role` — planner / implementer / reviewer;
2. `task` — architecture / code / context / localized / review / arbitration;
3. `tier` — senior / executor по неопределённости и риску;
4. `provider` и `runtime` — совместимый доступный поставщик и контур;
5. `effort` — поддерживаемый уровень, если его принимает выбранный режим.

Конкретный model ID выбирается из каталога runtime непосредственно перед вызовом. Новый релиз допускается после проверки необходимых инструментов, режима и полномочий; закрепления моделей и запрещённые замены задаёт проектный `method.md`. Не пытайся применить `effort` к режиму, который его не принимает. Для внешнего CLI передавай модель и effort явно, если применимо. Встроенное `inherit` разрешено только при совпадении требуемого профиля и доступного наследования.

Штатный Reviewer должен быть отделён новым контекстом и правами записи, а не обязательно поставщиком. Кросс-вендорная проверка применяется по критерию задачи либо при существенном конфликте оценок. Результат вызова, модель и ограничения подтверждаются метаданными инструмента; самоназвание модели в тексте не считается доказательством.

## Сбой и эскалация

- При недоступности модели или квоте выбери совместимый разрешённый runtime того же класса, не дублируя выполненные операции; проверь фактический профиль и непокрытые критерии.
- При смысловой ошибке оцени полноту задания и характер дефекта. Исправление известного дефекта остаётся в том же классе; архитектурный тупик, неоднозначный контракт или повторный содержательный дефект передаются Planner или старшей модели.
- При ошибке среды не меняй произвольно модель, не обходи разрешения и не объявляй обязательные проверки успешными.
- После fallback сохрани фактически полученный результат. Неподтверждённый обязательный поставщик или модель оставляют открытым только зависящий от них критерий.

Предпочитай достаточную по качеству, скорости и доступности модель. Никакая конкретная последовательность поставщиков и число резервов не обязательны. Точный резерв указывается только если его реально планируют использовать.
