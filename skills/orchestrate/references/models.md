# Выбор моделей и альтернатив

Модель выбирается по условиям конкретной задачи и роли. Роль, класс возможностей, `effort`, runtime и поставщик — разные свойства; имена выпусков, линейки и схемы именования моделей не являются частью протокола.

Рекомендации ниже — рабочие ориентиры, а не жёсткие очереди поставщиков или обязательные лестницы эскалации. Оркестратор подбирает достаточный профиль по неопределённости, цене ошибки, объёму контекста, задержке, доступности и квоте.

| Класс | Назначение |
|---|---|
| `senior` | Сложная архитектура, планирование при высокой неопределённости, содержательное ревью, кросс-вендорный арбитраж |
| `executor` | Инженерная реализация (код, SQL, тесты, конфигурации, рефакторинг), разведка контекста, документация, локальные правки и независимые подзадачи |
| `utility` | Вспомогательный лёгкий класс (когда доступен и оправдан): массовая классификация, первичный разбор, простое извлечение и базовая маршрутизация; не применяется для планирования, архитектуры и приёмки |

Внутри классов `senior` и `executor` модели могут различаться по пиковой глубине рассуждения, скорости и окну контекста (например, флагманская модель для экстремальной цены ошибки, модель с большим окном для анализа репозитория или быстрый нативный исполнитель для локальных правок) — выбор делается по фактическому каталогу runtime. Локальные модели (например, через Docker Model Runner и `docker agent`) допустимы для класса `utility`, приватных/офлайн-сценариев и простого резерва `executor` при достаточных локальных ресурсах.

Составной режим runtime (например, Antigravity Orchestrator) не является отдельным классом возможностей: он связывает планирующую и исполнительскую модели внутри **одной** сессии. Этот внутренний процесс не отменяет разделение ролей Planner, Implementer и Reviewer и не даёт Orchestrator права изменять продукт. Вызовы ролей выбираются по задаче. У составного или управляемого runtime (например, `docker ai` / Gordon) выбор модели и `effort` могут отсутствовать либо быть фиксированными.

## Профиль

До вызова роли определи:

1. `role` — planner / implementer / reviewer (либо внеролевая read-only разведка для `task: context`);
2. `task` — architecture / code / context / localized / review / arbitration;
3. `tier` — senior / executor / utility по неопределённости и риску;
4. `provider` и `runtime` — совместимый доступный поставщик и контур;
5. `effort` — поддерживаемый уровень, если выбранный runtime и режим его принимают.

Выбор или смена модели и настройка `effort` не являются обязательным условием: они применяются только когда выбранный runtime предоставляет такие параметры. Если runtime работает с фиксированным или управляемым профилем (например, Docker AI / Gordon, составные режимы или специализированные агенты без переключения модели и `effort`), вызов допустим с его штатным профилем без принудительной смены модели/`effort` и без замены runtime только ради переключения этих параметров — если задача не требует закреплённой модели по `method.md`, кросс-вендорного арбитража либо подтверждённого уровня рассуждения.

### Ориентиры по типу задачи

| Тип задачи (`task`) | Рекомендуемый класс | Стартовый `effort` | Когда менять класс или `effort` |
|---|---|---|---|
| `architecture` | `senior` | `high` | При экстремальной цене ошибки или легко упускаемых инвариантах — старшая доступная модель класса и/или максимальный поддерживаемый `effort` |
| `code` | `executor` | `medium` | Старт сразу с `high`, если заранее известны нетривиальные инварианты или связанные изменения; при архитектурном тупике или сложной диагностике — `senior` |
| `context` | `executor` (при массовом простом извлечении — `utility`) | `medium` (`low` для простого извлечения) | `high`, если нужно рассуждение по большому контексту в заданных границах; при нехватке качества `utility` предпочтительнее переход на `executor` |
| `localized` | Быстрый `executor` | `medium` (`low` для тривиальных правок) | Повышение `effort` или переход на более сильный профиль — только при выявленных скрытых зависимостях |
| `review` | `senior` | `medium` (ограниченная проверка); `high` (архитектура, риск, план) | Для типовых локальных правок без архитектурного риска допустим `executor` в независимом контексте |
| `arbitration` | `senior` другого поставщика | `high` | Максимальный поддерживаемый `effort` при сохраняющемся конфликте или высокой цене ошибки; поставщик не должен совпадать с автором проверяемого решения |

`effort` выбирается по неопределённости и цене ошибки, а не по роли: высокий уровень — для планирования и ревью плана, максимальный (`xhigh`/`max`) — когда результат зависит от легко упускаемых случаев (инварианты, конкурентность, читатели старой схемы), а не по умолчанию. Проходить промежуточные уровни не требуется, если сложность известна до старта. Поддерживаемый набор уровней `effort` зависит одновременно от модели и от конкретного runtime/канала — не предполагай наличие уровня, не подтверждённого каталогом выбранного runtime.

Конкретный model ID выбирается из каталога runtime непосредственно перед вызовом, если runtime поддерживает выбор модели; для управляемых и фиксированных профилей фиксируется сам runtime без подстановки вымышленного model ID. Новый релиз допускается после проверки необходимых инструментов, режима и полномочий; закрепления моделей и запрещённые замены при необходимости задаёт проектный `method.md`. Не пытайся применить выбор модели или `effort` к режиму, который их не принимает. Для внешнего CLI передавай модель и `effort` явно только если они поддерживаются выбранным runtime. Встроенное `inherit` разрешено только при совпадении требуемого профиля и доступного наследования.

Назначенный Reviewer должен быть отделён новым контекстом и правами записи, а не обязательно поставщиком. Для небольших ограниченных изменений не требуется отдельный проход Reviewer на каждый технический шаг. Кросс-вендорная проверка применяется по критерию задачи либо при существенном конфликте оценок. Для плана критерий — дорогая или необратимая ошибка: миграция схемы БД, изменение протокола или формата обмена, конкурентный доступ к общим ресурсам, транзакционные границы. Тогда целесообразна независимая оценка плана моделью класса `senior` другого поставщика; это не обязательная процедура для каждого пересмотра. Результат вызова, модель и ограничения подтверждаются метаданными инструмента; самоназвание модели в тексте не считается доказательством. Если runtime не возвращает метаданные модели, в отчёте фиксируется фиксированный/управляемый профиль runtime без утверждения конкретного model ID.

## Планирование по большому контексту

Если обязательные источники не помещаются в рабочий контекст Planner (крупный унаследованный код, десятки спецификаций, журналы), Orchestrator до вызова Planner выполняет read-only исследование (`task: context`) моделью с достаточным окном. Результат — список фактов с путями, версиями и способом проверки для поля «Источники» поручения Planner; структуры плана и выводов он не содержит. Разбиение на задачи и этапы остаётся за Planner класса `senior`.

## Сбой и эскалация

- При недоступности канала или исчерпании квоты сразу переключись на альтернативный аккаунт этого CLI (если настроен), другой доступный runtime той же модели (например, внутренний профиль в `agy` при лимите внешнего CLI) либо совместимый разрешённый профиль того же класса, не дублируя выполненные операции. Такое переключение выполняется автоматически по действующим правилам и не выносится пользователю как запрос на изменение правил или согласование замены.
- Если во время длительного автономного выполнения все разрешённые каналы требуемого класса исчерпали временное окно квоты (например, 5-часовой или аналогичный периодический лимит), передай фактический блокер и точку продолжения. Автоматическое многочасовое ожидание и повторное тестирование канала не запускай, если пользователь явно не поручил автономно ждать восстановления.
- При смысловой ошибке оцени полноту задания и характер дефекта. Известное исправление возвращается Implementer без обязательного нового цикла Planner и Reviewer; архитектурный тупик или изменившаяся цель передаются Planner либо более подходящей модели.
- При ошибке среды не меняй произвольно модель, не обходи разрешения и не объявляй обязательные проверки успешными.
- После переключения канала, fallback или порученного пользователем ожидания квоты сохрани фактически полученный результат и укажи использованный профиль и runtime в отчёте. Неподтверждённый обязательный поставщик или модель оставляют открытым только прямо зависящий от них критерий.

Предпочитай достаточную по качеству, скорости и доступности модель. Никакая конкретная последовательность поставщиков и число резервов не обязательны. Точный резерв указывается только если его реально планируют использовать.
