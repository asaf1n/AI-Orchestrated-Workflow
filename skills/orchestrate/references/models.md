# Модели, инструменты и альтернативы

Справочный материал оркестратора; читается по ссылке из [SKILL.md](../SKILL.md). Роли planner, implementer и reviewer эти файлы не читают.

Выбирай модель и уровень рассуждений соразмерно риску и объёму задачи по двум очередям с явными уровнями усилий (`low`, `medium`, `high`, `xhigh`):
- **Старшие модели (Tier 1):** `Opus` → `Astra` → `Argon`. Уровень `medium` применяется для ограниченной оценки и ревью; `high` — для архитектуры, проектирования и задач с высоким риском; `xhigh` допустим только для `Opus` и `Astra` при сохраняющейся сложности после оценки на `high` (для `Argon` наличие `xhigh` не предполагается).
- **Основные исполнители (Tier 2):**
  * `Sol` (`medium`; `high` до старта этапа при заранее известных нетривиальных инвариантах) — основная реализация: код, SQL, тесты, конфигурации, ограниченный рефакторинг.
  * `Flash` (`medium`; `low` для простого извлечения; `high` для задач с рассуждением в рамках определённых границ) — нативный исполнитель Antigravity: разведка репозитория, обработка материалов, документация, типовые изменения, независимые ограниченные подзадачи.
  * `Sonnet` (`medium`; `high` для сложной диагностики и длительных связанных изменений) — третий исполнитель: реализация и исправления по подготовленному заданию.

Инструменты используются для детерминированных сверок. Локальная LLM используется только при явном разрешении для извлечения и предварительной обработки со ссылками на источники; она не заменяет окончательные решения и независимую приёмку. Не создавай отдельный отчёт бюджета на каждый вызов.

Различай поставщика (Anthropic, OpenAI, Google), семейство модели и уровень усилия, конкретный идентификатор из каталога runtime (встроенный Antigravity, agy, claude, codex) и канал квоты/подписки. Встроенный Claude в Antigravity — модель Anthropic через Antigravity, а не Gemini и не внешняя подписка Claude Code. Имя модели в промпте, имя файла мнения и абстрактный псевдоним уровня в схеме субагента не подтверждают точную модель или независимость квоты.

Используемые поставщики, модели, уровень усилия и runtime уточняются перед запуском роли; номера версий моделей в инструкциях не закрепляются, а конкретные идентификаторы берутся из актуального каталога среды. Профиль роли выбирается явно по 6 базовым линиям сценариев. Наследование модели сессии допустимо для нативных сабагентов Antigravity (`Flash`, `Argon`), если модель хост-сессии совпадает с целевым профилем роли по линии сценария; для внешних CLI модель и усилие всегда задаются явно. Выбор не записывается как предметное решение. Рабочий выбор и цепочка альтернатив фиксируются в spec.md. Роль не переключает себе модель; определения ролей не закрепляют конкретную модель. После изменения модели сессии пользователем не называй прежнюю модель текущей.

При прочих равных в Antigravity сначала используй доступную внутреннюю модель нужного поставщика, затем внешнюю. Требования к качеству, независимому контексту, доступам и изоляции важнее порядка. Ограничение пользователя «только внутренние модели» исключает внешние CLI. Не считай все внутренние модели моделями Google: каталог `agy models` может содержать модели разных поставщиков (Google, Anthropic, OpenAI и открытые модели). Разрешённые параметры выбора модели и уровня рассуждений сверяй со схемой runtime; не приписывай абстрактным уровням схемы субагента (включая `inherit`) неизменные модели и поставщиков.

## Базовые линии сценариев (Маршрутизация по типам задач)

1. **Архитектура, проектирование и ТЗ с высокой неопределённостью:** `Opus (high)` → `Astra (high)` → `Argon (high)`
2. **Основная инженерная реализация (код, SQL, тесты, конфиги, рефакторинг):** `Sol (medium)` → `Flash (medium)` → `Sonnet (medium)` (при сложных инвариантах старт с `Sol (high)`)
3. **Разведка, сбор контекста, обработка материалов и документация:** `Flash (medium/low)` → `Sol (medium)` → `Sonnet (medium)`
4. **Типовые локальные правки и независимые параллельные подзадачи:** `Flash (medium)` → `Sol (medium)` → `Sonnet (medium)`
5. **Штатное независимое ревью этапа:** `Opus (medium)` → `Astra (medium)` → `Argon (medium)` (`high` для изменений с существенными последствиями)
6. **Кросс-вендорное ревью и арбитраж (сложные решения / конфликт оценок):** после Opus ревьюит `Astra (high)` → `Argon (high)`; после Astra/Sol ревьюит `Opus (high)` → `Argon (high)`

Это ориентир маршрутизации, а не доказательство доступности. Доступность и точный идентификатор проверяй по каталогу runtime и реальному ответу инструмента; фактическую замену называй в итогах. Явный выбор пользователя имеет приоритет перед базовыми линиями.

## Правила эскалации и замен

- На базовом исполнителе (`medium`) допускается максимум 1 итерация исправления по замечаниям ревью. Если та же содержательная ошибка воспроизводится повторно — не повышать усилие той же младшей модели до `high`, а проверить полноту ТЗ (`spec.md`) и сразу передать этап старшей модели Tier 1 (`high`).
- При исчерпании квот (HTTP 429) или отказе CLI — менять доступный канал/модель по очереди сценария без повышения усилия.
- Повышение усилия внутри класса допускается только по правилам очередей: `Sol (high)` до старта этапа при заранее известных нетривиальных инвариантах; `Sonnet (high)` для сложной диагностики и длительных связанных изменений; `xhigh` для Opus/Astra только при сохраняющейся сложности после оценки на `high`. Для Argon уровень `xhigh` не предполагается.
- Перед выдачей действующего spec.md выбранный уровень разрешается в конкретный идентификатор из текущего каталога runtime и параметр уровня усилия (либо явное наследование сессии); не перечисляй варианты через `/` в одной ячейке. При замене модели архитектурного/модульного рефакторинга желательно выполнить уже имеющиеся в проекте линтеры (`eslint`, `ruff`, `cargo clippy` по стеку), компиляцию и тесты; новые зависимости ради компенсации не добавляются. Подтверждай окончательное состояние результата и выполнение критериев разрешёнными проверками по контракту целевого сервиса. Для документации используй предметный словарь и исходные руководства. Для меньшего контекста предварительно фильтруй источники и разбивай их на связные части, сохраняя ссылки и ограничения. Не требуй публикации внутренней цепочки рассуждений: нужны проверяемое обоснование и доказательства.

При квоте или отказе используй следующий согласованный вариант модели и runtime; независимый поставщик нужен только при соответствующем критерии. Число резервов и поставщики определяются согласованным выбором и доступностью; обязательной цепочки из трёх поставщиков нет. Каждый выбранный вариант содержит одну модель; неиспользуемый резерв отмечается «не задан» или «не применяется». Смена модели внутри уже исчерпанного канала не считается независимым резервом без подтверждения runtime. Независимость компаний сама по себе не доказывает раздельную квоту внутренней подписки Antigravity.

Различай отказ модели, инструмента, канала квоты и целевой проверки. Не объявляй все модели недоступными по одному HTTP 429/503. Сохрани конкретный код и причину, оцени доступные альтернативы; при замене примени нужные проверки, словарь или фильтрацию контекста. Если все разрешённые варианты недоступны, сохрани точку продолжения и незавершённый результат; не выполняй продукт вместо роли. Недоступность обязательной проверки фиксируется отдельно. Замена модели сама по себе не является ни блокировкой проверки, ни приёмкой.

Причины различаются по фактическому ответу: HTTP 429/Insufficient Quota — квота или ограничение частоты; Context Exceeded — размер контекста; HTTP 503 — недоступность сервиса; ошибка запуска — инструмент. Antigravity CLI использует настроенный вход аккаунтом платформы; Claude Code и Codex — вход своего runtime. Их каналы и остатки не выводятся из общего имени Google или из наличия oauth-файла.

Фактическая модель подтверждается метаданными ответа или журналом инструмента; уровень рассуждений задаётся параметром вызова или профилем и подтверждается метаданными только в тех средах, которые его возвращают (отдельное протокольное поле в форме result.md для него не вводится). Если модель нельзя подтвердить, пиши «запрошена <модель>; фактическая модель не подтверждена»; работа не отклоняется только поэтому. Не выдавай утверждение самой роли за метаданные. В итогах назови фактические модель, runtime и замену с причиной.

Для независимого мнения сохраняй доступный идентификатор вызова/сессии и ссылку на исходный ответ с метаданными без секретов. Проверяй отдельно выбранную параметром модель, модель фактического ответа и автоматический fallback. При замене переименуй обозначение мнения по фактическому поставщику; отменённый или неуспешный вызов остаётся невыполненным. Если критерий требует ответ конкретной модели или разных поставщиков, неподтверждённый поставщик либо модель не закрывает этот критерий; продолжай разрешённые независимые части, а зависимое решение обозначь как неподтверждённое. Это не означает отказа от пригодного результата обычного исполнения из-за отсутствия метаданных.
