# Протокол оркестрации

Четыре роли ведут один план: планировщик, оркестратор, исполнитель, ревьювер. Этот документ — единственный общий протокол. Привязка проекта задаёт пути и предметный контракт и не пересказывает протокол заново. Если комплект недоступен, назови отсутствующий путь; не собирай процесс по старым отчётам. Подготовка проекта и необходимых файлов принадлежит оркестратору по [project-files.md](project-files.md); при разрешённой подготовке или работе отсутствие этих файлов не перекладывается на пользователя или исполнителя.

## Роли

**Планировщик** готовит новый план или существенно пересматривает существующий. До утверждения план проверяет независимый ревьювер. Планировщик исполнение не запускает.

Оркестратор привлекает planner для нового плана или существенного пересмотра: меняются цель, состав и порядок задач или этапов, зависимости, границы работ либо критерии приёмки. Для статуса, восстановления согласованного этапа, записи подтверждённых решений и результатов, исправления ссылок и формулировок без изменения смысла planner не нужен; эти правки выполняет оркестратор. Если восстановление выявило необходимость изменить план по существу, сначала обсуди изменение с пользователем, затем передай пересмотр planner. Пользователю не требуется отдельно вызывать planner или перечислять внутренние роли в поручении.

**Оркестратор** ведёт явно запущенный план. Правит инструкции, привязку и материалы плана. Этап сам не исполняет. Изменения инструкций тоже проходят независимое ревью.

**Исполнитель** выполняет один этап по действующему `spec.md` в новом контексте. Не коммитит. Не меняет файлы, закреплённые за оркестратором. `result.md` содержит факты, полученные исполнителем; незавершённый отчёт прерванного этапа дописывает исполнитель по своим артефактам, оркестратор свои измерения в отчёт не передаёт.

**Ревьювер** независимо проверяет план или полный результат этапа в новом контексте. Опирается на файлы, проверки и критерии, а не на пересказ. Не коммитит. Не меняет файлы оркестратора.

Над одним этапом работает один исполнитель. Следующий этап начинается после приёмки предыдущего. Параллельные исполнители одного плана не запускаются. Одновременно один план ведёт только одна сессия orchestrator; вторая сессия того же плана может только читать и докладывать статус, пока первая не завершена или явно не передала управление. Один план — один каталог текущей сессии.

## Модель

Поставщик модели — компания, чья модель и инструмент выполняют роль: Anthropic (Claude Code), OpenAI (Codex / ChatGPT), Google (Antigravity, Gemini CLI). Модель роли — конкретная модель поставщика, на которой работает роль, и уровень рассуждений, если инструмент его задаёт (`agy -p --effort`, `codex exec -c model_reasoning_effort=<уровень>`); без указания действует уровень по умолчанию инструмента.

### Оркестратор (модель-агностик)

Оркестратор не привязан к конкретному поставщику и может быть запущен в любой среде: Google (Antigravity, Gemini CLI), Anthropic (Claude Code) или OpenAI (Codex / ChatGPT). Оркестратор отвечает за подготовку и ведение процесса, декомпозицию, формирование контрактов этапов (`spec.md`), распределение ролей с учётом их профильных сильных сторон, приёмку и фиксацию состояния в git. Продуктовые изменения сам оркестратор не выполняет.

### Профильная специализация ролей по 3 поставщикам

Для решения задач этапа рекомендуются профильные инструменты и модели поставщиков, обладающие максимальной эффективностью в соответствующей области:

| Задача / Область | Рекомендуемый поставщик и модель | Сильная сторона / Почему |
|---|---|---|
| **Мультиагентная оркестрация и комплексные фичи** | Любая среда (модель-агностик); при запуске в Antigravity — Gemini 3.8 Flash / встроенные Claude 5.5, GPT-OSS | Параллельный запуск субагентов, единое окно артефактов, мультимодельный селектор, фоновые задачи. |
| **Сложный рефакторинг кода и критические модули** | OpenAI / Anthropic: GPT-6 Astra / Claude Opus 5.5 (для модульного: Sonnet 5.5) | Максимальная глубина рассуждений для архитектурных перестроек и критических модулей. |
| **Анализ тяжелых регламентов Минздрава / НСИ / большие дампы логов** | Google: Antigravity / Gemini CLI (Gemini 3.8 Flash / 3.1 Pro) | Огромный контекст (1M+ токенов): регламенты ЕГИСЗ и схемы СЭМД помещаются целиком без обрезки и потери связей. |
| **Глубокий алгоритмический анализ, оптимизация сложных SQL/PL-pgSQL** | OpenAI: Codex / ChatGPT (GPT-6.1 Sol / GPT-6 Astra) | Лучшая цепочка рассуждений (Reasoning) для нестандартной математики, планов запросов (EXPLAIN ANALYZE) и оптимизаций. |
| **Финальная вычитка документации и статей (Docusaurus / Вики)** | Anthropic: Claude Code (Claude Sonnet 5.5 / Haiku 4.5) | Чистый технический язык без траты дорогой квоты флагманских моделей (Opus/Astra). |

### Варианты назначения модели роли

Для роли доступны три варианта:

| Вариант | Как задаётся |
|---|---|
| Модель сессии | Роль наследует поставщика и модель текущей сессии. |
| Другая модель того же поставщика | Оркестратор задаёт модель роли параметром вызова роли либо неинтерактивным вызовом инструмента того же поставщика с указанием модели (`claude -p --model`, `codex exec -m`, `agy -p --model`). Если ни то ни другое недоступно, оркестратор предлагает пользователю сменить модель сессии и сам её не переключает. |
| Модель другого поставщика | Оркестратор вызывает инструмент другого поставщика в неинтерактивном режиме в корне проекта: `claude -p`, `codex exec`, `agy -p` (Antigravity CLI, вход аккаунтом Google) или `gemini -p` (Gemini CLI, ключ API). |

Без иного указания пользователя роль работает на модели сессии. Другой вариант выбирает оркестратор или пользователь при составлении плана или в начале новой сессии. Выбор действует до конца сессии и в материал плана не записывается; в пределах сессии он меняется по указанию пользователя или заменой из-за лимита или отказа инструмента. Поставщика и модель роли оркестратор называет в ответе с выбором варианта и в итоге этапа.

Для внешнего вызова задание называет путь к `SKILL.md` роли в установленном комплекте, корень проекта и точные пути `spec.md`, `result.md`, `review.md`; обмен идёт через те же файлы. Режим доступа внешнего вызова не шире роли. Исполнитель пишет в рабочее дерево проекта (`codex exec -s workspace-write`, `claude -p --permission-mode acceptEdits`, `agy -p --mode accept-edits`, `gemini -p --approval-mode auto_edit`); планировщик — материалы плана в границах, названных оркестратором. Ревьювер работает только на чтение; задание просит вернуть заключение итоговым ответом в форме `review.md`, и этот ответ сохраняет в `review.md` сам инструмент (`codex exec -s read-only -o <путь review.md>`, вывод `claude -p` в файл, поле `response` из `agy -p --output-format json`, вывод `gemini -p --output-format text` в файл); оркестратор этот ответ не правит и до приёмки сверяет по хешам, снятым до вызова, что `spec.md`, `result.md` и проверяемые файлы не изменились. При ненулевом коде выхода сохранённый файл отчётом не считается; оркестратор действует по разделу о восстановлении. Флаги обхода подтверждений и песочницы не используются. Проверки выполняются в пределах разрешений проекта; отказ записывается в отчёт роли как отказ среды и режим доступа не расширяет. Учётные данные инструмента оркестратор не настраивает. Если готового входа нет или в допустимом режиме роль не может записать свой файл обмена или вернуть заключение итоговым ответом, вариант недоступен.

Особенности неинтерактивного вызова и изоляции сред (включая Windows):
- В Windows PowerShell внешние CLI вызываются с закрытым потоком ввода (`$null | claude -p ...`, `$null | codex exec ...`, `$null | agy -p ...`, `$null | gemini -p ...`), что исключает зависание в ожидании stdin или задержки инструмента.
- Файлы отчётов сохраняются строго в кодировке UTF-8 без BOM. Для `claude -p` и `gemini -p --output-format text` перенаправление в PowerShell не должно использовать оператор `>`, создающий UTF-16LE: используется запись через `[System.Text.UTF8Encoding]::new($false)` или `Out-File -Encoding utf8`. Для `codex exec` используется встроенный ключ `-o <файл>`, для `agy -p --output-format json` извлекается поле `response`.
- Разделение инструментов и API Google:
  - **Antigravity CLI (`agy`)**: авторизация через аккаунт Google (`oauth_creds.json`), бэкенд платформы Antigravity. Поддерживает режимы `--mode <accept-edits|plan>` и глубину рассуждений `--effort <low|medium|high>`. Заключение возвращается в JSON-поле `response`.
  - **Gemini CLI (`gemini`)**: открытый CLI-инструмент (`@google/gemini-cli`), работающий через REST API Google AI Studio (`GEMINI_API_KEY`) или Google Cloud Vertex AI (ADC). Неинтерактивный вызов (`-p`) проверяет доверие каталогу (**Folder Trust**): в недоверенном каталоге инструмент аварийно завершается с кодом 55 (`FatalUntrustedWorkspaceError`). Чтобы не нарушать запрет на обходные флаги, каталог проекта предварительно регистрируется в файле доверия `~/.gemini/trustedFolders.json` (`{"<абсолютный_путь>": "TRUST_FOLDER"}`), либо при явном согласии пользователя вызов выполняется с переменной `GEMINI_CLI_TRUST_WORKSPACE=true`. Для исполнителя обязательно передаётся `--approval-mode auto_edit` (или `yolo` по прямому указанию пользователя) для предотвращения блокировки на интерактивных подтверждениях правки файлов. При наличии проектных определений в `.gemini/skills/` предупреждения `Skill conflict detected` считаются штатным переопределением проектным навыком глобального.
- Если проект использует виртуальное окружение Python (`.venv`), песочница `codex exec` требует указания флага `--add-dir "<путь_к_базовому_python>"` (значение `home` из `.venv/pyvenv.cfg`), иначе запуск `.venv/Scripts/python` блокируется песочницей как обращение к внешнему каталогу.
- Если `codex` не найден в `PATH` на Windows, оркестратор проверяет путь `%LOCALAPPDATA%\OpenAI\Codex\bin\*\codex.exe` и создаёт shim-скрипт `~/.local/bin/codex.cmd`. Если `agy` не найден в `PATH`, оркестратор проверяет путь `~/.gemini/bin/agy.exe` и создаёт shim-скрипт `~/.local/bin/agy.cmd`.
- Задание внешнему неинтерактивному ревьюверу формулируется как прямое однопроходное императивное действие («Выполни независимое ревью этапа прямо сейчас за один запуск...»), исключающее многошаговое диалоговое согласование готовности.

### Шаблон альтернатив при недоступности моделей и нехватке токенов

Если внешний инструмент недоступен (отсутствует CLI, нет авторизации, сбой сети) или исчерпан лимит токенов / квота (HTTP 429, Insufficient Quota, Context Exceeded), оркестратор не останавливает процесс и не объявляет этап заблокированным. Вместо этого применяется каскадное переключение альтернатив:

`Основная модель (Primary) -> Резерв 1 (Alternative 1) -> Резерв 2 (Alternative 2 / Модель сессии)`

**Принцип взаимного исключения звеньев (Mutual Exclusion Invariant):**
Каждая ячейка `spec.md` содержит ровно одну модель без дробей (`/`). Звенья цепочки строго независимы (`Primary ≠ Alternative 1 ≠ Alternative 2`):
- **Независимость поставщиков**: лимиты квот (HTTP 429, TPM, RPM) действуют на аккаунт поставщика в целом. Резерв 1 обязан использовать другого поставщика.
- **Резерв 2 и сессия**: если поставщик модели сессии совпадает с Основной или Резервом 1, в Резерв 2 назначается третий независимый поставщик (OpenAI ↔ Anthropic ↔ Google).
- **Атомарность**: ровно одна модель на ячейку (без `/` и вариантов).

Матрица альтернатив и стратегии компенсации (Degraded Mode):

| Специализация | Основная модель (Поставщик 1) | Резерв 1 (Поставщик 2, отличный от Основной) | Резерв 2 (Поставщик 3 / Сессия при несовпадении) | Стратегия компенсации (Degraded Mode) |
|---|---|---|---|---|
| **Архитектурный рефакторинг** | Anthropic: Claude Opus 5.5 | OpenAI: GPT-6 Astra | Google: Gemini 3.8 Flash (или модель сессии, если не совпадает с 1 и 2) | Обязательный запуск исполнителем строгих линтеров (`eslint`, `ruff`, `cargo clippy`), компилятора и тестов с фиксацией кодов выхода в отчёте. |
| **Модульный рефакторинг** | OpenAI: GPT-6 Astra | Anthropic: Claude Sonnet 5.5 | Google: Gemini 3.8 Flash (или модель сессии, если не совпадает с 1 и 2) | Обязательный запуск исполнителем линтеров и тестов с фиксацией кодов выхода в отчёте. |
| **Вычитка документации** | Anthropic: Claude Sonnet 5.5 | Google: Gemini 3.8 Flash | OpenAI: GPT-6.1 Sol (или модель сессии, если не совпадает с 1 и 2) | Использование строгого системного промпта со словарём терминов (ЕГИСЗ, РЭМД, ИЭМК, СЭМД, МО, НСИ) и правилами недопущения переводных калек. |
| **Алгоритмы и SQL/PL-pgSQL** | OpenAI: GPT-6.1 Sol / GPT-6 Astra | Anthropic: Claude Sonnet 5.5 (с высоким reasoning) | Google: Gemini 3.8 Flash (или модель сессии, если не совпадает с 1 и 2) | Принудительная пошаговая декомпозиция (Chain-of-Thought) в промпте: сбор плана `EXPLAIN ANALYZE`, проверка инвариантов, пошаговое доказательство. |
| **Тяжелые регламенты и логи** | Google: Gemini 3.8 Flash (High effort) / 3.1 Pro | Anthropic: Claude Sonnet 5.5 | OpenAI: GPT-6.1 Sol (или модель сессии, если не совпадает с 1 и 2) | Если контекст модели сессии меньше объёма данных — предварительная селективная фильтрация и чанкование данных оркестратором до вызова роли. |

Правила перехода и отчётности:

1. Оркестратор указывает цепочку альтернатив в `spec.md` (раздел «Модель и альтернативы»). Каждая ячейка содержит ровно одну конкретную модель. Звенья строго взаимно исключают друг друга (`Primary ≠ Alternative 1 ≠ Alternative 2`).
2. Об исчерпании лимита или недоступности судят по ответу или коду выхода вызова инструмента. Оркестратор автоматически переходит на Резерв 1 (независимый поставщик), а при его недоступности — на Резерв 2. Если поставщик модели сессии совпадает с уже отказавшим звеном, в Резерв 2 назначается оставшийся третий поставщик.
3. Переход на альтернативу не является блокировкой этапа. Состояние «проверка заблокирована» из-за замены не ставится.
4. В `result.md` исполнитель указывает фактическую модель исполнения. Оркестратор в итоге этапа в блоке «Как сейчас» докладывает факт замены: «Модель роли: <фактическая модель> (резерв вместо <основная>, причина: <лимит/недоступность>, стратегия: <компенсация>)».
5. Для варианта, отличного от модели сессии, оркестратор подтверждает модель роли по выводу или журналу инструмента, а не по ответу роли. Если подтверждения нет, в итоге этапа пишется «модель роли не подтверждена»; результат роли этим не отклоняется. Определения ролей модель не назначают. Роль не переключает себе модель.

## Явный запуск

Неявный запуск запрещён. Статус, утверждение и запуск — разные действия по смыслу, но не требуют отдельных команд. Ясного согласия или поручения в текущем диалоге достаточно; утверждение и запуск могут быть даны одной репликой после ревью. Не запрашивай их повторно, если они уже получены. Простое согласие с планом без поручения исполнять не считается запуском.

- **Статус.** Оркестратор докладывает подтверждённое состояние и расхождения. Исполнение не начинается.
- **Утверждение.** Пользователь принимает план после ревью. Оркестратор фиксирует в `00_summary.md` плановую отметку `Статус плана: утверждён ГГГГ-ММ-ДД`. Утверждение этапы не запускает. Существенный пересмотр утверждённого плана возвращает отметку в `черновик` до нового ревью и утверждения.
- **Запуск.** Пользователь явно разрешает исполнять утверждённые этапы. При прохождении явно запущенного утверждённого плана коммиты принятых этапов и переход к следующему разрешённому этапу входят в выполнение по умолчанию. Повторное разрешение на них не запрашивается; явный запрет или ограничение пользователя сохраняется. Push разрешается отдельно.
- **Продолжение.** Продолжается уже запущенный план. Работа за границами запуска и новые существенные решения сначала показываются пользователю.

Текст команды и имя плана — в [session-start.md](session-start.md). Отметки версии этапа и проверок — в [runtimes.md](runtimes.md).

## Где находится состояние

| Назначение | Место | В git |
|---|---|---|
| Очередь плана и ссылки на задачи | `orchestrate_workflow/plans/<план>/00_summary.md`, если контракт не назвал другой каталог | да |
| Цель, решения, этапы, критерии и единственное состояние этапов | материал задачи, раздел «Этапы задачи» | да |
| Привязка путей | `orchestrate_workflow/method.md` | да |
| Единственное действующее задание | `orchestrate_workflow/<план>/spec.md` | нет |
| Отчёт исполнителя | `orchestrate_workflow/<план>/result.md` | нет |
| Независимое ревью | `orchestrate_workflow/<план>/review.md` | нет |

Общий корень workflow — `orchestrate_workflow/`. В нём находятся файлы метода, постоянные материалы `plans/<план>/` и локальный каталог текущей сессии `<план>/`. Обязательные `spec.md`, `result.md`, `review.md` пишут роли по этому протоколу; рядом могут находиться другие локальные артефакты текущей сессии. Каталог сессии исключается из git локально по точному пути `/orchestrate_workflow/<план>/`; `orchestrate_workflow/plans/` остаётся под git.

Если контракт задаёт другой путь, используется он. Второй каталог состояния не создаётся. Имя `plans` зарезервировано и не используется как имя плана. Имена и пути существующего плана не меняются. Материалы закрытой задачи остаются на своих путях: архив и перенос при закрытии не создаются.

Оркестратор не выводит семантику из списка файлов каталога и не выбирает файл по сходству имени. В `orchestrate_workflow/plans/<план>/` задачами считаются только файлы, на которые явно ссылается `00_summary.md`. В `orchestrate_workflow/<план>/` состоянием протокола считаются только `spec.md`, `result.md`, `review.md`; остальные файлы игнорируются, пока на них нет явной ссылки из текущего задания, материала задачи или протокола. Каталоги других планов и сессий не читаются и не используются для восстановления текущего плана.

Очередь хранит ссылку и положение задачи, а не копию этапов и не второе состояние. В ней допускается только отдельная плановая отметка `Статус плана`; состояния этапов туда не копируются. Отметки версии и проверок пишутся только в материале задачи, форма — [runtimes.md](runtimes.md). Обязательные файлы обмена могут перезаписываться. Каталог текущей сессии не является вторым планом. Отдельного локального плана и копий будущих заданий нет. Утверждённое решение не остаётся только в чате или локальном артефакте. Номера редакций и попыток не вводятся.

Цель всего плана находится в `00_summary.md` или дана там точной ссылкой на цель в контракте проекта. Цель задачи находится в её материале. Цель не является вторым состоянием этапов; её не переносят между файлами при каждом ревью.

## Цикл этапа

1. Перед новым этапом исходная точка чистая, либо уже установлено, кому принадлежат существующие правки. Чужие правки не удаляются, не прячутся и не коммитятся.
2. Оркестратор пишет один `spec.md` со ссылкой на материал и этап, точными идентификаторами `План`, `Задача`, `Этап`, исходным `HEAD` и состоянием рабочего дерева на момент выдачи. Для нового этапа исходная точка чистая либо существующие правки явно перечислены с установленной принадлежностью и проверенной версией; те же сведения обязательны при восстановлении. Посторонние правки сохраняются и не включаются в результат этапа. При явном запрете коммитов исходная точка включает проверенные незакоммиченные результаты предыдущих этапов; их не принимают и не проверяют заново только из-за отсутствия коммита. Критерии не слабее материала задачи и датированных решений.
3. Отчёт предыдущего вызова заменяется строкой ожидания из [templates.md](templates.md). Старый отчёт не выдаётся за результат нового задания.
4. Исполнитель в новом контексте читает контракт, привязку, задание и названные источники. В `result.md` без изменения переносит идентификаторы `План`, `Задача`, `Этап`, исходный `HEAD` и описание исходного рабочего дерева из `spec.md`. Проверяет чистоту форматирования через `git diff --check`. Не коммитит.
5. Ревьювер в новом контексте сначала проверяет совпадение `План`, `Задача`, `Этап`, исходного `HEAD` и исходного рабочего дерева в `spec.md` и `result.md`, затем сверяет изменения от указанной исходной точки и критерии, включая `git diff --check`. В `review.md` переносит те же идентификаторы. Несовпадение идентификаторов означает, что отчёт не относится к текущему заданию и не может быть принят.
6. Приёмка возможна только при вердикте «принято» и выполненных критериях. Конец вызова и старый отчёт приёмку не подтверждают.
7. Состояние этапа обновляется в материале задачи. После независимой приёмки результат и это состояние фиксируются одним коммитом без повторного вопроса, если пользователь явно не запретил коммиты. Чужие изменения в коммит не включаются. При явном запрете коммита этап отмечается «Принят ГГГГ-ММ-ДД без коммита» с причиной и проверенной версией файлов; запрет не заменяется вопросом о повторном разрешении.
8. Следующий исполнитель получает новый `spec.md` и новый контекст.

Принадлежность означает соответствие изменения границе этапа, а не установление личности автора. При восстановлении отдельно указываются исходный HEAD продукта, последующие коммиты процесса, уже закоммиченная непринятая реализация и текущие незакоммиченные правки. Чистое дерево и наличие коммита не подтверждают приёмку; исходный HEAD не заменяют ради чистой точки. Новые необходимые пути явно добавляются в границу до вызова исполнителя.

Восстановление уже начатого этапа сначала устанавливает принадлежность имеющихся изменений. Исключение из этого правила действует, только если оно явно записано в материале задачи и названо по этапу. Новые этапы записанное исключение само не охватывает.

## Начало и восстановление сессии

Порядок и тексты команд — в [session-start.md](session-start.md).

Если каталога текущей сессии нет, задача не объявляется неначатой. Если идентификаторы `План`, `Задача`, `Этап` или исходный `HEAD` в задании и отчётах не совпадают, старый отчёт не принимается: сначала устанавливается результат ранее вызванной роли. При обрыве операции среды не повторяются лишь из-за отсутствия отчёта. Завершение роли по лимиту или ошибке фиксируется как незавершённое: оркестратор сохраняет полученные сообщения, отдельные коды выхода и явные пути доказательств, проверяет фактические изменения и последствия. При неизвестном результате сначала читают состояние; повтор не разрешается одним отсутствием `result.md`. Восстановленные сведения не выдаются за полный отчёт исполнителя или независимое ревью.

Отрицательное ревью, недоступная проверка и неизвестный результат обрыва — разные ситуации. Старое положительное ревью не отменяет оформленный возврат. До вызова исполнителя пути и состояние обязательных `spec.md`, `result.md`, `review.md` сверяются с привязкой и текущим заданием; уже установленные пути повторно не согласуются.

При отмене задания оркестратор помечает `spec.md` отменённым и сохраняет точку остановки: завершённые операции, их последствия и явные ссылки на доказательства. Отмена исполнения не удаляет реализацию и не принимает этап. До нового поручения исполнитель не вызывается.

Точка остановки записывается до итогового ответа, даже если исполнитель не успел оформить отчёт. Оркестратор отделяет собственную запись восстановления от отчёта исполнителя и отмечает неизвестные результаты проверок. Перед заявлением о завершении проверяет состояние вызванных им ролей и фоновых команд; сообщение об остановке, ещё ожидающее доставки, не подтверждает завершение. Восстановление не разрешает оркестратору выполнять продукт вместо остановленного исполнителя.

## Задание

До выбора параметров и критериев, зависящих от объёма или потока данных, устанавливается фактическая основа из разрешённых проектом источников. Материал плана содержит источник, период, предельную дату, определение показателя и ограничения измерения. Тестовые данные не заменяют оценку рабочего потока. Если обязательный замер недоступен, зависимое решение не объявляется обоснованным; независимая часть подготовки продолжается. Разрешённое контрактом чтение не откладывается до этапа внедрения только потому, что источник относится к production.

`spec.md` — единственное действующее задание. В нём обязательны `План`, `Задача`, `Этап`, исходный `HEAD`, состояние исходного рабочего дерева, ссылка на материал, границы путей, проверки и, если этап продолжается, восстановительные действия. Прежние вопросы и отчёты новым разрешением не становятся.

Задание не меняется одновременно с исполнением. Сначала фиксируется безопасная точка: что уже изменено, какие последствия это имеет и как продолжать. Обновление не отправляется второй инструкцией работающей роли. После остановки при возврате `spec.md` переписывается целиком.

Исправление после отчёта также оформляется полным новым `spec.md` и передаётся исполнителю в новом контексте. Возобновление прежнего агента сообщением с дополнительным заданием не заменяет этот порядок. В материале задачи заменяются утратившие силу критерии и отметки; прежний текст сохраняется только для объяснения точки восстановления, с явным указанием его времени и статуса.

Короткая реплика не разрешает дополнительную бизнес-логику. Если реплика неоднозначна и расширила бы логику, останавливается только зависимое расширение. Предположение не записывается как согласованное решение и не дописывается в задание работающего исполнителя.

Исполнитель не меняет файлы вне перечня в `spec.md`.

Перед вопросом или новым правилом читаются контракт, предметный источник и действующее решение. Вопрос о новом существенном выборе сопровождается фактом и ссылкой. Повтор уже согласованного не запрашивается. Новое существенное решение сначала представляется пользователю и после утверждения записывается в материал задачи. Разрешение пользователя действует в своих границах всё время задания; повторное подтверждение уже разрешённой операции не вводится из-за смены роли или отсутствия отчёта. Предметные решения и ограничения среды остаются отдельными вопросами.

## Проверки и приёмка

Эталон приёмки — критерии материала задачи и датированные решения. Ослабление критерия и исключения вне этих критериев недопустимы. Исключение требует отдельного решения пользователя и явных критериев оставшейся работы.

Возврат ревьювера нельзя превратить в приёмку переносом замечаний в следующий этап.

Неизмеренное не записывается как факт.

Для проверки среды обязательны конкретные критерии. Ответ интерфейса и текст страницы не заменяют визуальную проверку, когда она задана.

Известное падение называется по проверке и причине. У каждой команды виден собственный код выхода. Команда, которая отрезает вывод, и следующая успешная команда не маскируют ошибку.

Для проверки данных сначала устанавливается минимальный связный набор источников и периодов. Число падений не заменяет причину каждого.

Недоступная проверка получает состояние «проверка заблокирована». Это не приёмка и не автоматический откат. Препятствие среды отделяется от дефекта результата.

### Автоматическое тестирование и пирамида проверок

Автоматические тесты (`tests/`) обеспечивают быструю обратную связь для автономных агентов и разработчиков:
1. **Назначение регулярного набора (`tests/`):** Обслуживает исключительно **работоспособность и инварианты сервисов платформы** (PostgreSQL DWH, Airflow, Superset, API, клиенты).
2. **Изоляция аналитики и разовых действий:**
   - Регулярный сьют не должен содержать прикладных отчетов бизнес-аналитики (например, расчет долей сигналов ЕГИСЗ, анализ не связанных документов) и проверок частных отраслевых случаев.
   - Тяжелые разовые процедуры (двойной накат DDL схемы, исторический глубокий ребилд за месяцы) и предметные сценарии выносятся в автономный архив (`scripts/scenarios/`) и запускаются вручную или в CI, а не через регулярный `pytest`.
3. **Пирамида и жесткие SLA скорости:**
   - **Tier 0 (Static, <1с, без внешних сервисов):** AST DAG, манифесты k8s, архитектурные DDL-контракты схемы.
   - **Tier 1 (Unit, <3с, без внешней БД):** Модульные проверки логики с моками внешних сервисов.
   - **Быстрый цикл Tiers 0+1 (<3–5с):** Обязателен перед фиксацией любых промежуточных изменений и сдачей этапа исполнителем.
   - **Tier 2 (Интеграционный DWH/БД, <45–60с):** Инварианты движка БД (партиции, инкременты, расчет дат, функции классификации).
   - **Tier 3 (E2E / UI / API, <30–40с):** Приемочные проверки дашбордов, фильтров и SQL Lab на стенде.
   - **Полный DoD (`pytest tests`):** <60–90с.
4. **Запрещенные антипаттерны:**
   - Построчный regex-поиск по файлам кода/схем вместо компиляции и валидации логики.
   - Раздутая построчная параметризация частных случаев (схлопывать однотипные кейсы в компактные пакетные проверки инвариантов).
   - Смешивание слоев (unit-тесты не лезут в БД; тесты ядра БД не проверяют UI-манифесты; тесты сервисов не гоняют скрипты развертывания).
   - Загрязнение состояния (транзакции с `ROLLBACK`, изоляция тестовых данных).

Ревью обязательно для каждого этапа и для существенного изменения инструкций.


### Проверенная версия и закрытие замечаний

Ревью относится к конкретному содержимому: в заключении указаны исходный HEAD, точный перечень проверенных файлов и SHA-256 их содержимого либо коммит, если все эти файлы соответствуют ему. Неизменность только HEAD не подтверждает неизменность рабочего дерева. Перед приёмкой или разрешённым коммитом оркестратор сверяет текущие файлы с этой версией. Изменённые после ревью файлы и затронутые ими критерии снова проверяются; прежний вердикт на них не распространяется.

Для каждого замечания возврата ревьювер называет нарушенный критерий, последствие и признак закрытия. Предложения по стилю отделяются от замечаний, влияющих на исполнение или приёмку. Сообщение «исправлено» или «передано» не закрывает замечание: требуются фактическая правка и проверка признака закрытия. Повторное ревью охватывает исправленные места и их связи; полный повтор нужен при изменении цели, границ или критериев. При повторяющихся возвратах сначала сверяют устойчивость задания и исходных требований, а не добавляют новые правила на каждом проходе.

### Ревью плана или инструкций

Оркестратор задаёт режим, проверяемые пути, исходный HEAD и явный путь заключения по [templates.md](templates.md). Такое ревью не использует идентичность незавершённого продуктового этапа и не перезаписывает его отчёты. Заключение — доказательство проверки, а не второе место состояний этапов. Положительное ревью плана не заменяет утверждение пользователя и команду запуска.

При переработке плана сначала проверяют сохранение решений, границ и критериев, затем форму текста. В результате планировщика даётся краткое соответствие исходных требований новым местам; это доказательство переноса, не копия плана. Дата решения берётся из источника; неизвестная дата помечается как неизвестная. Дата предложения, исполнения и принятия не смешивается.

## Текущие файлы и возврат

В материале задачи — решения и состояние. В `spec.md` — только текущее задание. Формы файлов — в [templates.md](templates.md).

Для нового вызова файл отчёта этой роли заменяется строкой ожидания. Пока она на месте, отчёта нет.

При возврате вердикт остаётся фактом возврата, пока не начат новый вызов. `spec.md` переписывается целиком под замечания и исходные критерии. Исполнитель получает новый контекст. Предыдущий `result.md` заменяется строкой ожидания.

Приёмка после возврата заново сверяет исходные критерии и замечания возврата.

## Отказы среды

Отказ сообщается конкретно: какое действие отклонено и какая причина названа, если она дана. Граница отказа не распространяется на всю задачу и не превращается в утверждение, что пользователь не разрешил работу.

Право пользователя, правила проекта и решение классификатора среды — разные факты.

Гипотеза о внутренней причине классификатора не выдаётся за установленный факт. Смена настроек разрешений, новый доступ или запись секрета не предлагаются без установленной необходимости. Настройки разрешений не меняются, чтобы обойти отказ.

Разрешение пользователя, правило в файле настроек, загруженная политика сессии, отказ инструмента и доступ к целевой системе проверяются отдельно. Наличие `allow` не доказывает выполнение команды, отказ классификатора не доказывает отсутствие сетевого доступа или прав БД. Перед вопросом о доступе сверяются действующие решения и доступные настройки без чтения значений секретов. Если причина отказа не названа, она остаётся неизвестной; способ исправления не объявляется проверенным без подтверждения. Исторические ограничения не восстанавливаются как действующие правила без поручения пользователя.

Отклонённое действие не повторяется в расчёте на случайное разрешение и не переносится в другую роль как обход. Один и тот же текст команды может быть то отклонён, то выполнен; из этого не следует ни что отказа не было, ни что нужна особая фраза.

Текст навыка отказ среды не отменяет. Пока отказ действует, недоступная операция отделяется от уже разрешённой независимой работы. Обещание больше не останавливаться процесс не исправляет.

## Принадлежность файлов

При изменении общего комплекта инструкций оркестратор сверяет связанные навыки, формы состояния, шаблоны и проектные привязки. Независимое ревью относится к точной версии исходников и фактическим файлам затронутого проекта; HEAD репозитория навыков не подтверждает состояние другого репозитория. Установленный комплект обновляется только после положительного ревью проверяемой версии. После переноса сверяются хеши файлов; пользовательские метаданные и локальные дополнения сохраняются. Обрыв ревью оставляет комплект непринятым и не разрешает его распространение.

| Кто пишет | Что |
|---|---|
| Оркестратор | контракт инструкций, файлы метода, определения ролей, каталог плана |
| Планировщик | материал задачи в границах, названных оркестратором |
| Исполнитель | продукт в перечне `spec.md`, затем `result.md` |
| Ревьювер | `review.md`, если задание ревью не расширено; при внешнем вызове только на чтение — итоговый ответ, который сохраняет инструмент |

Исполнитель и ревьювер не коммитят. При прохождении утверждённого запущенного плана коммит после приёмки делает оркестратор по умолчанию, если пользователь явно не запретил коммиты. Затем он докладывает итог этапа по [templates.md](templates.md#ответ-по-итогу-этапа) и продолжает следующий разрешённый этап. Вопросы — только при новых условиях или конфликтах, требующих решения пользователя. Push — отдельное разрешение.

## Чего не делать

- Не создавать второй план, второе задание и второе состояние этапа.
- Не принимать этап без ревью и без сверки с критериями.
- Не ослаблять критерий молча.
- Не читать отсутствие каталога текущей сессии как отсутствие работы.
- Не запускать работу из статусного отчёта.
- Не назначать модель в определении роли и не выбирать модель роли вне вариантов раздела «Модель».
- Не вести номера попыток и архив копий заданий.
- Не дописывать предположение в задание работающей роли.
