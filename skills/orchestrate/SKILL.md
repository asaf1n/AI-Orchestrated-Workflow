# Оркестрация и общий протокол

Этот SKILL.md содержит общий протокол, подключение проекта, начало сессии, формы состояния и задание этапа. Формы материала плана находятся в [planner](../planner/SKILL.md), результата — в [implementer](../implementer/SKILL.md), заключения — в [reviewer](../reviewer/SKILL.md). Все инструкции и шаблоны находятся в SKILL.md этих четырёх навыков; каталог references не используется.

Прочитай существующие `AGENTS.md`, `orchestrate_workflow/method.md` и названные ими предметные источники. Привязка задаёт проектные пути и отклонения; общие правила в проект не копируются. Если установленный комплект недоступен, назови точный отсутствующий путь. Не восстанавливай протокол из старых отчётов.

## Роли и принадлежность

| Роль | Работа и право записи |
|---|---|
| Оркестратор | Ведёт процесс; правит инструкции, привязку, определения ролей, очередь и отметки состояния задач. Продукт этапа не реализует. |
| Планировщик | В новом контексте готовит новый план или существенный пересмотр в названных оркестратором границах. Исполнение не запускает. |
| Исполнитель | В новом контексте выполняет один этап по spec.md, меняет только разрешённые пути, приносит result.md. Не коммитит. |
| Ревьювер | В новом контексте независимо проверяет план, инструкции или окончательную версию результата. Не правит продукт, инструкции и план; не коммитит. |

Оркестратор вызывает planner при изменении цели, состава или порядка задач и этапов, зависимостей, границ либо критериев. Статус, восстановление в согласованных границах, запись подтверждённых решений и редактура без изменения смысла planner не требуют. Существенное изменение сначала обсуждается с пользователем.

Право planner менять материал задачи ограничено поручением оркестратора. После независимой приёмки явно запущенного утверждённого этапа коммит делает оркестратор; он включает результат и отметку состояния, сохраняет чужие правки и продолжает следующий разрешённый этап. Явный запрет коммитов сохраняется. Push требует отдельного разрешения. Для работы над инструкциями вне такого запуска коммит выполняется только по поручению пользователя.

Незавершённый result.md дописывает исполнитель по своим доказательствам. Оркестратор не подменяет его отчёт собственными правками продукта или измерениями; собственную сверку оформляет отдельно с явной ссылкой. Возврат не превращается в приёмку переносом замечаний в следующий этап.

Если оркестратор обнаружил дефект продукта, он передаёт исполнителю наблюдение, критерий и признак исправления через полное новое задание. При явно порученной пользователем смене роли сначала завершает текущий вызов, фиксирует передачу и начинает исполнение в новом контексте; свою реализацию сам не принимает. Найденное смешение авторства отражается в сверке, а исходный отчёт сохраняется до установления фактов. Исправление result.md поручается ответственному исполнителю; независимое ревью проводится заново для итоговой версии.

## Разрешение и состояние

Статус, утверждение и запуск различаются по смыслу. Ясное согласие или поручение в диалоге достаточно; обязательной формулы нет. Утверждение после ревью и запуск можно дать одной репликой. Согласие с планом само по себе не запускает исполнение.

- Статус остаётся чтением: не создаёт план, не подключает проект, не запускает роли исполнения.
- Новый план и существенный пересмотр имеют `Статус плана: черновик` до независимого ревью и утверждения пользователя.
- После утверждения оркестратор записывает `Статус плана: утверждён ГГГГ-ММ-ДД` в очередь. Новый этап запускается только у утверждённого плана.
- Продолжение сохраняет действующие разрешения, ограничения, остановку и исходные критерии. Новые существенные решения предъявляются пользователю; уже согласованное не запрашивается повторно.

В Codex используется `$orchestrate`, в Claude и Antigravity — обнаруженный `/orchestrate`. Примеры поручений:

```text
/orchestrate Создай план <имя>. Цель: <результат>. Исполнение не запускай.
/orchestrate Запусти утверждённый план <имя>. Push запрещён.
/orchestrate Продолжи запущенный план <имя>. Сначала сверь материал, git, отчёты и процессы.
/orchestrate Доложи подтверждённое состояние плана <имя>. Исполнение не запускай.
```

| Назначение | Путь по умолчанию | Хранение |
|---|---|---|
| Привязка | orchestrate_workflow/method.md | git |
| Цель, статус и очередь плана | orchestrate_workflow/plans/<план>/00_summary.md | git |
| Цель задачи, датированные решения, этапы и их состояние | orchestrate_workflow/plans/<план>/<задача>.md | git |
| Текущее задание, результат, ревью | orchestrate_workflow/<план>/spec.md, result.md, review.md | локально, вне git |

Очередь содержит ссылки, а не копии этапов. Task-файлы выбираются только по ссылкам из очереди. В текущей сессии протокольны только spec.md, result.md, review.md; другие файлы читаются только по явной ссылке из материала, задания или поручения. Отдельного локального плана, копий будущих заданий, номеров попыток и архива закрытых задач нет. Материал закрытой задачи остаётся на прежнем пути. Имя `plans` зарезервировано и не используется как имя плана.

У этапа одна текущая отметка в разделе «Этапы задачи» материала:

| Отметка | Условие |
|---|---|
| Не начат | Исполнитель не вызывался. |
| В работе | Задание выдано, приёмки нет. |
| Принят ГГГГ-ММ-ДД | Независимое ревью принято, все критерии выполнены. Результат и отметка фиксируются одним коммитом. |
| Принят ГГГГ-ММ-ДД без коммита | Пользователь запретил коммиты; рядом причина и проверенная версия файлов по SHA-256. |
| Возврат | Названы незакрытые критерии; следующий этап не начинается. |
| Проверка заблокирована | Названа недоступная проверка и буквальная причина среды; это не дефект результата и не приёмка. |

Рядом с границей этапа стоят «Готово» с критериями и фактические проверки: прошла, упала с причиной, не запускалась с причиной. Исключение допустимо только по критериям или отдельному решению пользователя. Число падений не заменяет разбор причин. При приёмке прежние отметки возврата и план восстановления убираются; дробный номер этапа — его имя, а не номер попытки. Оркестратор меняет состояние только после сверки факта и вердикта.

## Начало сессии и восстановление

До вызова роли:

1. Прочитай контракт, привязку, очередь со статусом, материал текущей задачи и критерии. Сверь всё поручение: что выполнено, что осталось, какие разрешения действуют.
2. Сопоставь материал с git log, HEAD, рабочим деревом, spec/result/review и активными ролями и командами. Для отчётов проверь пять идентификаторов: `План`, `Задача`, `Этап`, `Исходный HEAD`, `Исходное рабочее дерево`.
3. Установи принадлежность существующих изменений по границе задания. Чужие изменения не удаляются, не прячутся и не коммитятся. Отдельно назови исходный HEAD продукта, последующие коммиты процесса, закоммиченную непринятую реализацию и незакоммиченные правки. Чистое дерево или коммит не доказывают приёмку; исходный HEAD не заменяется ради чистой точки.
4. Прочитай вызываемые сценарии, чтобы не дублировать выполняемые ими операции. Не добавляй backup, новые копии состояния или операции среды без необходимости. Для сравнения до/после задай одинаковые данные, обе точки состояния и обработку показателей, зависящих от времени.
5. Проверь точные пути, установленный навык роли, доступность инструмента, выбранную модель и ресурсы. Доложи подтверждённое состояние и расхождения; запускай только разрешённую работу.

Отсутствие каталога текущей сессии или result.md не доказывает отсутствия работы. При неизвестном результате сначала сверяются реальные файлы, процессы, БД и последствия; выполненная операция не повторяется лишь из-за обрыва отчёта. Незавершённый отчёт не выдаётся за приёмку. Старое положительное ревью не отменяет оформленный возврат.

При стопе или отмене прекрати выдавать новые задания, останови принадлежащие вызову роли и команды и проверь их конечный статус. До ответа сохрани отмену в spec.md и точку остановки: завершённые операции, последствия, доказательства и неизвестные результаты. Не продолжай без нового поручения. Если пользователь просит только ответ, сводку или Textile, сформируй этот ответ по имеющимся фактам; запрос отчёта не разрешает продуктовые действия.

Задание не меняется одновременно с исполнением. Сначала останови роль и зафиксируй точку; при возврате перепиши spec.md целиком под исходные критерии и замечания, замени result.md строкой ожидания и вызови нового исполнителя. Исправление после отчёта также требует полного задания и нового контекста. Оркестратор не исправляет продукт вместо остановленного исполнителя.

Одновременно один план ведёт одна orchestrator-сессия. Другая сессия этого плана читает статус до явной передачи управления. Передача называет оставшуюся работу, активные процессы и владельцев ресурсов; локальные отчёты не перезаписываются, пока их использует работающая роль.

## Совместная работа и ресурсы

В одном последовательном этапе — один ответственный исполнитель; следующий зависимый этап начинается после приёмки предыдущего. Разрешённые независимые исследования, оценки разных моделей и проверки изолированных частей могут идти параллельно. Параллельная реализация разрешается только в явно разделённых границах поручения; она не создаёт второе состояние плана или общий перезаписываемый spec.md.

Каждому участнику передай корень/песочницу, точный SKILL.md, режим, входные источники и исходную версию, перечень принадлежащих ему файлов, точный путь собственного ответа и список общих ресурсов. Сообщи, что другие участники работают рядом: чужие правки сохраняются. Независимые аналитические ответы получают разные пути и не заменяют spec/result/review действующего этапа; дополнительная аналитика не становится очередным обязательным ревью без основания.

Изоляция контекста, файлов и внешних ресурсов проверяется отдельно. Новый агент или worktree не изолирует PostgreSQL, Superset, Kubernetes, порты, курсоры и общий файл отчёта. На изменение каждого общего ресурса назначается один владелец. DDL, исторический пересчёт, provisioning и живые тесты, которые зависят от них, выполняются последовательно либо на отдельных проверенных контурах. Нельзя одновременно накатывать схему и тестировать тот же DWH. Ревью проверяет стабильную окончательную версию после остановки записи в неё.

До параллельного запуска заполни раздел «Общие ресурсы» spec.md: точный контур без секретов, требуемый доступ, владелец и порядок передачи. Даже тест с ROLLBACK меняет состояние внутри транзакции и может конфликтовать по блокировкам. Два набора живых тестов запускаются параллельно только при доказанной совместимости данных, блокировок и фикстур либо на отдельных БД. Если изоляция не установлена, используй последовательный порядок; параллельное чтение стабильного состояния и независимая работа с файлами сохраняются. Перед передачей проверь завершение принадлежащих владельцу процессов и отсутствие продолжающихся изменений; отмена задачи сама по себе ресурс не освобождает. Эта запись находится в текущем spec.md и не создаёт отдельный реестр или механизм блокировки.

В Antigravity используй фактически доступный `invoke_subagent` и его текущую схему. `inherit` разделяет workspace; `branch` создаёт отдельный Git worktree; `share` разделяет хранилище каталогов и не считается доказанной изоляцией записи. Полученный абсолютный путь и изменения проверяются до использования результата. Команда Mercurial `hg share` не описывает Git worktree. Возможность параллельного запуска не доказывает владение ресурсами. См. [официальное описание субагентов](https://antigravity.google/docs/subagents/) и [Teamwork](https://antigravity.google/docs/teamwork/).

Для независимых оценок дай одинаковое исходное поручение и критерии нескольким реально вызванным моделям; собери ответы, разногласия и доказательства до выбора решения. Не предписывай ревьюверу положительный вердикт и не заменяй мнение недоступной модели текстом другой модели «от её лица».

Пока фоновые роли или команды выполняются, продолжай независимую разрешённую работу. Используй уведомления среды или ограниченное ожидание изменения статуса без частого опроса; уведомление о промежуточном ответе не означает завершение. Перед новым зависимым действием и итогом проверь конечный статус всех вызванных участников и команд. Исследовательский SQL имеет явный statement_timeout и ограниченный период/объём по контракту проекта; таймаут подключения не заменяет ограничение выполнения SQL. Не запускай неограниченный полный скан потоковой таблицы ради аналитической пробы.

## Модели, инструменты и альтернативы

Различай поставщика модели (Anthropic, OpenAI, Google), конкретную модель, runtime (встроенный Antigravity, agy, claude, codex, gemini) и канал квоты/подписки. Встроенный Claude в Antigravity — модель Anthropic через Antigravity, а не Gemini и не внешняя подписка Claude Code. Имя модели в промпте, имя файла мнения и `model: pro` не подтверждают точную модель или независимость квоты.

Без другого выбора роль наследует модель сессии. Другую модель или поставщика выбирает оркестратор/пользователь при планировании либо в начале сессии; выбор не записывается как предметное решение. Рабочий выбор и цепочка могут указываться в текущем spec.md. Роль не переключает себе модель; определения ролей не закрепляют конкретную модель. После изменения модели сессии пользователем не называй прежнюю модель текущей.

При прочих равных в Antigravity сначала используй доступную внутреннюю модель нужного поставщика, затем внешнюю. Требования к качеству, независимому контексту, доступам и изоляции важнее порядка. Ограничение пользователя «только внутренние модели» исключает внешние CLI. Не считай все внутренние модели Google: каталог `agy models` может содержать Gemini, Claude и GPT-OSS. Разрешённые значения Model/модельные tiers сверяй со схемой runtime; не приписывай `pro`, `flash`, `flash_lite`, `inherit` неизменные модели и поставщиков.

Профильные варианты по действующему выбору проекта; в каждом конкретном вызове выбирается одна модель:

| Работа | Основная | Резерв 1 | Резерв 2 |
|---|---|---|---|
| Алгоритмы и SQL/PL-pgSQL | OpenAI GPT-6.1 Sol | Anthropic Claude Sonnet 5.5 | Google Gemini 3.8 Flash |
| Архитектурный рефакторинг | Anthropic Claude Opus 5.5 | OpenAI GPT-6 Astra | Google Gemini 3.8 Flash |
| Модульный рефакторинг | OpenAI GPT-6 Astra | Anthropic Claude Sonnet 5.5 | Google Gemini 3.8 Flash |
| Тяжёлые регламенты, логи и независимые оценки | Google Gemini 3.8 Flash | Anthropic Claude Sonnet 5.5 | OpenAI GPT-6.1 Sol |
| Вычитка документации | Anthropic Claude Sonnet 5.5 | Google Gemini 3.8 Flash | OpenAI GPT-6.1 Sol |

Это варианты, а не доказательство доступности или качества. До запуска проверяй каталог и реальный ответ инструмента. Недоступное имя не заменяется молча похожим. Актуальный пользовательский выбор имеет приоритет перед таблицей.

Варианты того же профиля выбираются явно: GPT-6 Astra вместо GPT-6.1 Sol для сложного SQL; Gemini 3.1 Pro вместо Flash для тяжёлого рассуждения; Haiku 4.5 для ограниченной вычитки, если качества достаточно. Не перечисляй варианты через `/` в ячейке действующего задания. При резерве архитектурного/модульного рефакторинга выполняются уже имеющиеся в проекте линтеры (`eslint`, `ruff`, `cargo clippy` по стеку), компиляция и тесты; новые зависимости не добавляются ради компенсации. Для SQL подтверждай алгоритм планом EXPLAIN ANALYZE и проверкой инвариантов в разрешённом контуре. Для документации используй предметный словарь и исходные руководства. Для меньшего контекста предварительно фильтруй источники и разбивай их на связные части, сохраняя ссылки и ограничения. Не требуй публикации внутренней цепочки рассуждений: нужны проверяемое обоснование и доказательства.

При квоте или отказе переходи по разрешённой цепочке на следующего независимого поставщика. Основная, Резерв 1 и Резерв 2 используют три разных поставщика; каждая ячейка spec.md содержит одну модель без `/`. Модель сессии подходит для резерва только при несовпадении с предыдущими поставщиками. Смена модели внутри уже исчерпанного канала не считается независимым резервом без подтверждения runtime. Независимость компаний сама по себе не доказывает раздельную квоту внутренней подписки Antigravity.

Различай отказ модели, инструмента, канала квоты и целевой проверки. Не объявляй все модели недоступными по одному HTTP 429/503. Сохрани конкретный код и причину, оцени доступные альтернативы; при замене примени нужные проверки, словарь или фильтрацию контекста. Если все разрешённые варианты недоступны, сохрани точку продолжения и незавершённый результат; не выполняй продукт вместо роли. Недоступность обязательной проверки фиксируется отдельно. Замена модели сама по себе не является ни блокировкой проверки, ни приёмкой.

Причины различаются по фактическому ответу: HTTP 429/Insufficient Quota — квота или ограничение частоты; Context Exceeded — размер контекста; HTTP 503 — недоступность сервиса; ошибка запуска — инструмент. Antigravity CLI использует готовый вход аккаунтом платформы; Gemini CLI — настроенный способ входа своего runtime. Их каналы и остатки не выводятся из общего имени Google или из наличия oauth-файла.

Модель подтверждается метаданными ответа или журналом инструмента. Если её нельзя подтвердить, пиши «запрошена <модель>; фактическая модель не подтверждена»; работа не отклоняется только поэтому. Не выдавай утверждение самой роли за метаданные. В итогах назови фактические модель, runtime и замену с причиной.

Для независимого мнения сохраняй доступный идентификатор вызова/сессии и ссылку на исходный ответ с метаданными без секретов. Проверяй отдельно выбранную параметром модель, модель фактического ответа и автоматический fallback. При замене переименуй обозначение мнения по фактическому поставщику; отменённый или неуспешный вызов остаётся невыполненным. Если критерий требует ответ конкретной модели или разных поставщиков, неподтверждённый поставщик либо модель не закрывает этот критерий; продолжай разрешённые независимые части, а зависимое решение обозначь как неподтверждённое. Это не означает отказа от пригодного результата обычного исполнения из-за отсутствия метаданных.

### Внешние вызовы

Используй отдельный неинтерактивный запуск в корне проекта. В промпте назови точный SKILL.md роли, корень, режим, входы и пути обмена; не переписывай туда вместо файла всё задание. Новый контекст не подменяется продолжением прежнего агента.

| Инструмент | Исполнение | Ревью |
|---|---|---|
| Claude Code | claude -p --model <модель> --permission-mode acceptEdits | claude -p --model <модель> --permission-mode plan; разрешены только нужные инструменты чтения/проверок |
| Codex | codex exec -m <модель> -s workspace-write | codex exec -m <модель> -s read-only -o <путь заключения> |
| Antigravity CLI | agy -p --model <идентификатор> --mode accept-edits --effort <уровень> | agy -p --model <идентификатор> --mode plan --output-format json |
| Gemini CLI | gemini -p --model <модель> --approval-mode auto_edit | gemini -p --model <модель> --approval-mode plan --output-format json |

Перед использованием сверяй `--help`, `--version`, путь executable, отдельный код выхода и реальный ответ. Наличие CLI или расширения не доказывает доступ к модели. Авторизацию и настройки разрешений ради обхода отказа не меняй; секреты не читай и не публикуй. Флаги обхода подтверждений и песочницы не используются.

В Windows PowerShell закрывай stdin: `$null | <CLI> ...`. Сохраняй stdout и stderr отдельно, а код CLI сразу после его завершения; последующая команда его не заменяет. Отчёты записываются UTF-8 без BOM через явный UTF8Encoding; не полагайся на кодировку `>` или версии PowerShell. Для JSON сохраняй только содержимое result/response в заключение, сохранив метаданные и ошибку отдельно. При ненулевом коде сохранённый файл не является успешным отчётом.

Внешний ревьювер возвращает полное заключение итоговым ответом; инструмент/оркестратор сохраняет его без правки. До и после вызова сравни SHA-256 spec.md, result.md и проверяемых файлов. Чтение установленного комплекта вне workspace должно быть реально разрешено; при отказе назови действие и причину, не расширяй режим. Шаблон промпта: «Выполни независимое ревью прямо сейчас за один запуск по <SKILL.md>, <входам> и <критериям>. Только чтение. Выбери вердикт по фактам. Верни заключение по форме навыка».

Доверие Gemini workspace проверяется отдельно; недоверенный каталог может вернуть код 55. Отказ Folder Trust не обходится переменной окружения или сменой каталога. Python `.venv` может ссылаться на внешний базовый interpreter: для разрешённого Codex-вызова используй `--add-dir` с `home` из pyvenv.cfg, если требуется этой песочницей. Недоступные CLI сначала проверяются по известному пути установки; настройка shim выполняется только в рамках порученного подключения.

На Windows известные пути проверки: `%LOCALAPPDATA%/OpenAI/Codex/bin/*/codex.exe`, `~/.gemini/bin/agy.exe`; shims при порученном подключении — `~/.local/bin/codex.cmd`, `~/.local/bin/agy.cmd`. Проверяй текущую установку, а не предполагай существование бинарника по этому шаблону. Для заранее порученного доверия каталогу Gemini использует `~/.gemini/trustedFolders.json` с записью `{"<абсолютный_путь>": "TRUST_FOLDER"}`; существующее доверие сначала читается, само по себе поручение на роль не разрешает менять настройки доверия ради обхода отказа. Способ входа Gemini CLI может быть аккаунтом, API key или Vertex AI; доступ определяется фактическим вызовом, секреты из файлов не читаются.

## Проверки и приёмка

Эталон — материал задачи и датированные решения. spec.md не ослабляет их. Перед аналитическими решениями, зависящими от потока, измерь разрешённый реальный источник: период, предельная дата, определения показателей и ограничения. Локальные тестовые числа не заменяют поток. При недоступном замере зависимое решение остаётся неподтверждённым; независимая подготовка продолжается.

Каждая обязательная команда должна завершиться. Код 0 фиксируется только после конечного статуса, чтения вывода и проверки ожидаемого результата. `RUNNING`, ID процесса, отсутствие ошибки, начало тестов и старый лог не доказывают успех. Отчёт не заполняется успехами заранее. Каждая команда имеет собственный код выхода; цепочка через `;` и код последней команды не служат доказательством предыдущих. Не отрезай диагностический вывод так, чтобы скрыть ошибку.

Связывай проверки с окончательной версией файлов. После изменений повтори затронутые проверки; не переносись на старый положительный результат. Полный повтор нужен, когда изменились границы, критерии или связи. Перед приёмкой сверь версию ревью с текущими файлами по SHA-256 либо точному коммиту при соответствии всех файлов. Визуальная проверка, если задана, не заменяется ответом HTTP или текстом страницы.

Регулярные tests проверяют работоспособность и инварианты платформы и сервисов. Разовая бизнес-аналитика, частные отраслевые сценарии, двойной накат DDL и глубокие пересчёты живут в scripts/scenarios или аналогичном архиве и запускаются отдельно. Regex-поиск подстрок вместо выполнения/компиляции, раздутая построчная параметризация и смешивание unit/БД/UI/развёртывания не допускаются. Живые тесты изолированы, детерминированы и гарантируют ROLLBACK без загрязнения курсоров.

Пирамида: Tier 0 static <1 с, Tier 1 unit с моками <3 с, быстрый цикл 0+1 <3–5 с перед фиксацией и сдачей, Tier 2 БД <45–60 с, Tier 3 UI/API <30–40 с, полный DoD <60–90 с. Команды и предметные критерии берутся из контракта проекта; DWH/DAG требуют соответствующих интеграционных проверок. Изменение только инструкций проверяется валидацией навыков, ссылок, форматирования и поведения, без запуска продуктовых развёртываний.

Для схемы/развёртывания требуемые два прогона выполняются отдельно от регулярного pytest с собственными командами и кодами. Второй чистый прогон подтверждается сравнением соответствующего постоянного состояния, а не только кодом 0. Измерения исполнителя и независимая повторная проверка различаются явно.

Недоступная проверка не называется дефектом реализации и не требует отката сама по себе. Отказ среды, разрешение пользователя, локальная настройка allow и фактический доступ — разные факты. Проверяй их отдельно без чтения секретов. Не приписывай неназванную причину классификатору; не повторяй отклонённое действие ради случайного разрешения и не передавай его другой роли как обход.

## Цикл этапа

Перед передачей результата reviewer оркестратор сопоставляет обязательные проверки из spec.md со строками result.md: команда, доступный идентификатор запуска, конечный статус, код, вывод и версия файлов. Путь лога и идентификатор без прочитанного результата не служат доказательством. Отчёт об успехе до завершения проверки возвращается исполнителю; до исправления он не используется для приёмки. Если проверка ещё работает, состояние остаётся «В работе»; при остановке фиксируется незавершённый результат. Оркестратор не дописывает отсутствующие доказательства в отчёт исполнителя.

Поручение reviewer содержит исходные критерии, полный diff, фактический результат и форму с незаполненным вердиктом. Не включай желаемый вердикт и положительные заключения других моделей как инструкцию. Отчёт исполнителя доступен как проверяемое утверждение; сравнение самостоятельных мнений проводится после их получения. Завершение CLI само по себе не является приёмкой: проверь полный ответ reviewer, обоснование каждого обязательного критерия и соответствие хешей.

1. Установи исходную точку и принадлежность правок, подготовь полное spec.md по форме ниже, включая восстановление после обрыва, если требуется.
2. Для нового вызова замени только отчёт вызываемой роли строкой ожидания. Не уничтожай результат незавершённого прежнего вызова до установления его фактического состояния.
3. Вызови исполнителя в новом контексте по [implementer](../implementer/SKILL.md), передав точные пути. Дождись завершения роли и обязательных команд, проверь отчёт и финальную версию.
4. Вызови независимого ревьювера в новом контексте по [reviewer](../reviewer/SKILL.md). Передай критерии и нейтральную форму, не готовый положительный вердикт.
5. При возврате сохрани его как факт, подготовь полное исправленное spec.md и новый вызов исполнителя. Замечание закрывается фактической правкой и проверкой признака закрытия.
6. При вердикте «принято» сверь все критерии и неизменность проверенной версии, обнови материал и выполни разрешённый коммит результата вместе со статусом. Неуспешный коммит не позволяет перейти к следующему этапу. При явном запрете запиши приёмку без коммита с причиной и SHA-256.
7. Доложи итог и продолжи следующий разрешённый этап без повторного согласования, если нет новых условий или конфликтов. Отчёт сам по себе план не останавливает.

Сначала прочитай существующие AGENTS, CLAUDE, GEMINI, README, привязку и роли. Создавай только недостающее, сохраняй пользовательские настройки и предметные правила. Не меняй доступы, секреты, инфраструктуру и зависимости ради подключения.

Создай одну привязку по форме ниже. Не создавай orchestrate_workflow/references, копии SKILL.md и дополнительные method.md. При удалении старых копий сначала сопоставь содержимое, перенеси проектные отличия в привязку, исправь действующие ссылки. В контракте зафиксируй предметные источники, проверенные команды и принадлежность файлов; неизвестное не придумывай. Для Claude отсутствующий CLAUDE.md, для Antigravity отсутствующий GEMINI.md содержит `@AGENTS.md`; существующие сохраняются.

Определения ролей — тонкие файлы `.codex/agents/<роль>.toml`, `.claude/agents/<роль>.md` либо определения текущего API Antigravity. Файл Antigravity нельзя объявлять рабочим только по аналогии с Claude: проверь обнаружение и схему. Новые папки и определения заранее не создаются.

## Обновление комплекта

Исходный Git-репозиторий навыков — источник истины. До изменения проверь его фактический путь, remote, HEAD, origin/main и рабочее дерево; установленную копию сравнивай с актуальными исходниками, сохраняя локальные дополнения. Изменения всех четырёх навыков, форм и затронутых привязок проходят независимое ревью точной версии до установки.

После положительного ревью перенеси проверенные файлы в фактические каталоги обнаружения runtime, сохрани пользовательские agents/openai.yaml и другие настройки. Удаляй только проверенные устаревшие файлы в границах поручения; прежде проверь абсолютные пути и всех вызывающих. Сверь SHA-256 содержимого после установки и повторного переноса. Уже запущенные сессии могут содержать прежние инструкции: для следующего вызова используй новый контекст и проверь путь загруженного SKILL.md. Обрыв ревью не разрешает распространение комплекта.

Для сверки Git-рабочего дерева можно использовать [snapshot.py](scripts/snapshot.py): он читает HEAD, diff, индекс и содержимое изменённых/неотслеживаемых файлов. Игнорируемые файлы, submodules и внешние сервисы его снимком не покрываются; spec/result/review и состояние БД проверяются отдельно.
